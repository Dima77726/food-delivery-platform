# Food Delivery Platform

Модульный монолит доставки еды на Spring Boot 4 и Java 21: рестораны, меню, корзина, заказ,
оплата, доставка, уведомления и журнал аудита.

Проект учебный, но написан по боевым правилам: транзакционный outbox для событий, сквозная
метка запроса, идемпотентная оплата, миграции Liquibase, интеграционные тесты на настоящих
PostgreSQL, Redis и Kafka через Testcontainers.

---

## Быстрый старт

Нужны Docker и Docker Compose. JDK ставить не обязательно — сборка идёт внутри образа.

```bash
cp .env.example .env
docker compose --profile full up -d --build
```

Профиль `full` поднимает и само приложение. Без него стартует только инфраструктура —
это режим для разработки, когда приложение запускается из IDE.

| Что | Адрес |
|---|---|
| API | http://localhost:8080/api/v1 |
| Swagger UI | http://localhost:8080/swagger-ui.html |
| Kafka UI | http://localhost:8090 |
| Prometheus | http://localhost:9090 |
| Grafana | http://localhost:3000 |

Служебный порт приложения (8081) наружу не публикуется намеренно: `/actuator/prometheus`
и `/actuator/health` доступны только внутри сети compose, где живёт Prometheus.

### Проверить, что всё поднялось

```bash
curl http://localhost:8080/api/v1/restaurants
```

Миграции создают три ресторана с меню, так что список не будет пустым.

## Разработка

Инфраструктура в Docker, приложение — из IDE:

```bash
docker compose up -d
```

Дальше запускается `FoodDeliveryPlatformApplication`. Значения по умолчанию в
`application.yml` рассчитаны ровно на этот режим: база на `localhost:5432`, Kafka
на `localhost:9094` — внешний листенер брокера.

### Тесты

Два круга, и разделены они намеренно:

```bash
./mvnw test      # быстрый круг: без Docker, сами тесты — меньше секунды
./mvnw verify    # + интеграционные на Testcontainers, около двух минут
```

Основное время первой команды уходит не на тесты, а на генерацию из OpenAPI
и компиляцию.

Surefire гоняет классы `*Test` — доменные правила и обработчик ошибок. Failsafe гоняет `*IT`
на настоящих контейнерах: именно они проверяют SQL, транзакции и кэш.

Обратите внимание на имена: surefire забирает не только `*Test.java`, но и `Test*.java`,
поэтому интеграционный тест нельзя называть `TestSomethingIT` — он попадёт в быстрый круг
и утащит туда контейнеры.

Перед коммитом нужен `verify`, во время работы достаточно `test`.

## Устройство

Модульный монолит: модули разделены по предметной области, а не по слоям.

```
service/src/main/java/com/dima/fooddelivery/
├── restaurant/    рестораны
├── menu/          категории и блюда
├── cart/          корзина
├── order/         заказ, его статусы и outbox
├── payment/       оплата и возвраты
├── delivery/      назначение курьера и доставка
├── notification/  очередь уведомлений
├── audit/         журнал действий
├── user/          пользователи, роли, аутентификация
├── admin/         админский API
└── common/        кэш, безопасность, Kafka, метрики, обработка ошибок
```

Внутри модуля — четыре слоя: `api` (контроллеры и мапперы), `domain` (типы предметной
области), `persistence` (доступ к данным), `service` (логика).

Модули не лезут в чужие таблицы. Корзина спрашивает цену блюда у `MenuService`, а статус
ресторана — у `RestaurantService`. Правило живёт в одном месте и меняется в одном месте.

### Четыре подхода к доступу к данным

Это осознанный разнобой, а не наследие: одна кодовая база показывает четыре способа
работать с базой и цену каждого.

| Модуль | Подход | Что на нём видно |
|---|---|---|
| `restaurant` | Spring Data JPA | derived-запросы; грязная проверка вместо UPDATE |
| `menu` | Spring Data JPA | `@OneToMany`, cascade, `orphanRemoval`, `LEFT JOIN FETCH` против N+1 |
| `user` | Hibernate вручную | `EntityManager`, JPQL, `@ElementCollection` для ролей |
| `payment` | Hibernate вручную | Criteria API; массовое обновление в обход контекста |
| `order`, `cart`, `delivery`, `notification` | Spring JDBC | рукописный SQL, `RowMapper`, `FOR UPDATE SKIP LOCKED` |
| `audit` | голый JDBC | `Connection`, `PreparedStatement`, ручной разбор строк |

Все четыре работают поверх одного `DataSource` и одного менеджера транзакций
(`JpaTransactionManager`): `JdbcTemplate` берёт соединение через `DataSourceUtils`
и попадает в ту же транзакцию, что и `EntityManager`.

Подробности каждого решения — в javadoc соответствующих репозиториев. Отправная точка —
`AuditLogRepository`: там же объяснено, почему голый JDBC обязан брать соединение
у `DataSourceUtils`, а не у `DataSource`.

### База данных

Схемой владеет Liquibase, и только он. Hibernate работает с `ddl-auto: validate` —
сверяет сущности с таблицами на старте и падает при расхождении, но ничего не меняет.

Миграции лежат в `service/src/main/resources/db/changelog/migrations/`, каждая ссылается
на файл с SQL. Прикладные таблицы живут в схеме `food_app`, журнал Liquibase — в
`liquibase_meta`.

### События и надёжность

Смена статуса заказа пишется в таблицу `order_event_outbox` в той же транзакции, что и сам
заказ. Отдельная задача разбирает очередь и отправляет события в Kafka. Так событие
не может уехать по откатившейся транзакции, а недоступный брокер не роняет оформление
заказа.

Продюсер идемпотентный, `acks=all`; необработанные сообщения уходят в DLT.

### Наблюдаемость

Каждый запрос получает `X-Correlation-Id` (или использует присланный) и возвращает его
в ответе. Метка попадает в MDC и видна в каждой строке лога, включая фоновые задачи
и потребителей Kafka — по ней запрос прослеживается насквозь:

```bash
docker compose logs app | grep <correlation-id>
```

Метрики отдаёт Actuator в формате Prometheus, дашборд Grafana поставляется в
`observability/grafana/provisioning/`.

## API

Источник истины по контракту — `openapi/food-delivery-api.yaml`. Из него генерируются
интерфейсы контроллеров для `service` и типизированный клиент в модуле `client`,
поэтому контракт сервера и контракт клиента не могут разъехаться.

Спецификация пока описывает рестораны и меню; живой контракт для остальных модулей отдаёт
springdoc на `/swagger-ui.html`.

Готовая Postman-коллекция на весь API — в `postman/`, там же инструкция.

### Аутентификация

JWT, роли `CUSTOMER`, `RESTAURANT_OWNER`, `COURIER`, `ADMIN`. Роль `ADMIN` через
регистрацию не выдаётся: первый администратор создаётся при старте из `APP_ADMIN_EMAIL`
и `APP_ADMIN_PASSWORD`, а если они не заданы — не создаётся вовсе.

## Сборка

```bash
./mvnw clean verify           # сборка и все тесты
docker compose --profile full build   # образ приложения
```

Модуля два: `service` — приложение, `client` — типизированный Java-клиент к нему,
отдельный артефакт. Разделены по потребителю: клиента можно отдать, не отдавая
приложение со всеми его зависимостями.
