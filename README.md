# Food Delivery Platform

Платформа доставки еды на Spring Boot 4 и Java 21: рестораны, меню, корзина, заказ,
оплата, доставка, уведомления и сводный журнал аудита. Плюс пять модулей поверх пяти разных
хранилищ — отзывы, трек курьера, аналитика, рекомендации и поиск.

Проект переехал с модульного монолита на микросервисы — постепенно, по одному сервису
(см. [Микросервисы](#микросервисы)). Монолита больше нет: за единым шлюзом работают семь
сервисов — пользователи, каталог, уведомления, заказы, платежи, трек курьера и insights
(отзывы, аналитика, рекомендации, GraphQL).
Синхронно сервисы разговаривают по gRPC, асинхронно — через Kafka; оплата заказа — сага
поверх Kafka с outbox и inbox на обеих сторонах.

**Репозитории.** Код сервисов живёт в отдельных репозиториях, у каждого своя история, свой CI
и свой образ. Этот репозиторий — платформа: Docker Compose, наблюдаемость, Postman и общая
документация, ничего из кода сервисов здесь нет.

| Репозиторий | Что в нём |
|---|---|
| [food-delivery-platform](https://github.com/Dima77726/food-delivery-platform) | этот: compose, `observability/`, `postman/`, `docker/`, документация |
| [food-delivery-contracts](https://github.com/Dima77726/food-delivery-contracts) | контракты: события Kafka, gRPC, OpenAPI и клиент; публикуются в GitHub Packages |
| [food-delivery-api-gateway](https://github.com/Dima77726/food-delivery-api-gateway) | шлюз |
| [food-delivery-identity-service](https://github.com/Dima77726/food-delivery-identity-service) | пользователи, вход, токены |
| [food-delivery-catalog-service](https://github.com/Dima77726/food-delivery-catalog-service) | рестораны, меню, поиск |
| [food-delivery-order-service](https://github.com/Dima77726/food-delivery-order-service) | корзина, заказ, доставка, сага оплаты |
| [food-delivery-payment-service](https://github.com/Dima77726/food-delivery-payment-service) | платежи |
| [food-delivery-notification-service](https://github.com/Dima77726/food-delivery-notification-service) | уведомления |
| [food-delivery-tracking-service](https://github.com/Dima77726/food-delivery-tracking-service) | трек курьера |
| [food-delivery-insights-service](https://github.com/Dima77726/food-delivery-insights-service) | отзывы, аналитика, рекомендации, сводный аудит, GraphQL |

Пути вида `order-service/src/...` в этой документации — это пути внутри репозитория
соответствующего сервиса. Все репозитории разом клонирует `scripts/clone-services.sh`.

Проект учебный, но написан по боевым правилам: транзакционный outbox для событий, сквозная
метка запроса, идемпотентная оплата, миграции Liquibase, интеграционные тесты на настоящих
PostgreSQL, Redis и Kafka через Testcontainers.

## Быстрый старт

Нужны Docker и Docker Compose. Ни JDK, ни исходников сервисов не нужно: compose подтягивает
готовые образы из GitHub Container Registry, которые собирает CI репозиториев сервисов.

```bash
cp .env.example .env
# замените в .env заглушки change-me-* на свои значения, а JWT_PRIVATE_KEY — на ключ:
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 | openssl pkcs8 -topk8 -nocrypt -outform DER | base64 -w0
docker login ghcr.io     # если образы приватные: логин GitHub и токен с правом read:packages
docker compose --profile full pull
docker compose --profile full up -d
```

Ни одного пароля в репозитории нет: у учётных данных не осталось значений по умолчанию
ни в `application.yml`, ни в `docker-compose.yml`. Незаполненный `.env` — это остановка
на старте с именем недостающей переменной, а не молчаливый запуск под чужим паролем.
Полный список переменных с пояснениями — в [.env.example](.env.example).

Профиль `full` поднимает и сами сервисы: шлюз, пользователей, каталог, уведомления,
заказы, платежи, трек курьера и insights (вместе с Cassandra — его хранилищем). Без него
стартует только инфраструктура — это режим для разработки, когда сервисы запускаются из IDE.

| Что | Адрес |
|---|---|
| API (через шлюз) | http://localhost:8080/api/v1 |
| Swagger UI (insights) | http://localhost:8080/swagger-ui.html |
| GraphQL / песочница GraphiQL | http://localhost:8080/graphql, http://localhost:8080/graphiql |
| Kafka UI (профиль `tools`) | http://localhost:8090 |
| RabbitMQ (интерфейс управления) | http://localhost:15672 |
| Mailpit (письма уведомлений) | http://localhost:8025 |
| MinIO (консоль; фото блюд) | http://localhost:9001 |
| Prometheus | http://localhost:9090 |
| Grafana | http://localhost:3000 |

Наружу опубликован только шлюз. Сервисы, как и их служебные порты (8081),
доступны только внутри сети compose: `/actuator/prometheus` и `/actuator/health` видит
Prometheus, а снаружи их не видно.

### Память

Стек рассчитан на ноутбук с 16 ГБ. У каждого долгоживущего контейнера есть `mem_limit`,
а JVM-сервисы берут под кучу 60% своего лимита (`Dockerfile` в репозитории сервиса). Без лимита JVM считает своей
всю виртуальную машину Docker, и восемь сервисов вместе вытесняют остальное — первыми
падают контейнеры Testcontainers с ошибкой 500 от Docker.

| Что | Потолок |
|---|---|
| Инфраструктура: PostgreSQL, Redis, Kafka, RabbitMQ | ~2,4 ГБ |
| Prometheus и Grafana | 0,6 ГБ |
| Tempo, Loki, Alloy | ~1 ГБ |
| Восемь сервисов (профиль `full`, без Cassandra) | ~4,2 ГБ |
| Cassandra (входит в `full`) | 1,5 ГБ |
| MongoDB, Neo4j, ClickHouse, Elasticsearch (профиль `stores`) | ~3,8 ГБ |
| Kafka UI (профиль `tools`) | 0,5 ГБ |

Это потолки, а не расход: реально стек занимает заметно меньше. Но всё сразу — около 13 ГБ
потолков, поэтому на 16 ГБ поднимайте только то, с чем работаете. Интеграционные тесты
поднимают собственные контейнеры; полный стек на время их прогона лучше остановить.

Docker Desktop на WSL 2 по умолчанию отдаёт виртуальной машине половину памяти. Файл
`%UserProfile%\.wslconfig` поднимает потолок и добавляет подкачку на пиковые моменты:

```ini
[wsl2]
memory=9GB
swap=8GB
```

Остальные 7 ГБ остаются Windows, IDE и локальной модели AI-агента. После правки —
`wsl --shutdown` и перезапуск Docker Desktop.

### Проверить, что всё поднялось

```bash
curl http://localhost:8080/api/v1/restaurants
```

Миграции каталога создают три ресторана с меню, так что список не будет пустым.

### Пять дополнительных хранилищ

MongoDB, Cassandra, Neo4j, ClickHouse и Elasticsearch живут под отдельным профилем
и по умолчанию выключены. Вместе они просят около пяти гигабайт памяти, а нужны только тем
модулям, которые с ними работают, — поэтому обычный `docker compose up -d` их
не поднимает и приложение стартует ровно так же, как стартовало без них.

Cassandra здесь особая: с треком курьера она уехала в tracking-service и стала его
единственным, обязательным хранилищем. Выключателя у неё больше нет, а поднимается она
и с профилем `full`.

Включение состоит из двух шагов, и оба обязательны:

```bash
docker compose --profile stores up -d
```

затем в `.env` снять комментарий с нужных строк:

```
STORE_MONGO_ENABLED=true
STORE_NEO4J_ENABLED=true
STORE_CLICKHOUSE_ENABLED=true
STORE_ELASTICSEARCH_ENABLED=true
```

Выключатели независимы: можно поднять только MongoDB и включить только отзывы.

Порядок важен. Включённый модуль требует доступного сервера: свою схему он создаёт на старте
и при недоступном хранилище не даёт приложению подняться. Это сделано намеренно — молча
стартовавший сервис с наполовину рабочим API обнаружился бы много позже и по жалобе.

| Что | Адрес |
|---|---|
| Neo4j Browser | http://localhost:7474 |
| Elasticsearch | http://localhost:9200 |
| ClickHouse HTTP | http://localhost:8123 |
| MongoDB | localhost:27017 |
| Cassandra | localhost:9042 |

Neo4j и ClickHouse ходят под учётными записями из `.env` — `NEO4J_USERNAME`/`NEO4J_PASSWORD`
и `CLICKHOUSE_USER`/`CLICKHOUSE_PASSWORD`. Значений по умолчанию у них нет: включённый
модуль без своей переменной останавливает приложение и называет её. Compose передаёт
те же значения контейнерам, при запуске из IDE их нужно задать в конфигурации запуска.

Пользователем ClickHouse нельзя делать `default`: скрипт образа пытается создать уже
существующего пользователя и падает. А без явной учётной записи образ закрывает `default`
сетевой доступ, и приложение получает `Authentication failed` вместо соединения.

В DataGrip: host `localhost`, port `8123`, database `food_delivery`, логин и пароль — из `.env`.

После изменения учётной записи пересоздай контейнер командой
`docker compose --profile stores up -d --no-deps --force-recreate clickhouse`.
Именованный том с данными сохраняется. Healthcheck выполняет `SELECT 1` с аутентификацией:
один `/ping` не проверяет возможность приложения выполнять запросы.

## Разработка

Сервисы разрабатываются каждый в своём репозитории. Клонировать все разом:

```bash
scripts/clone-services.sh ..          # рядом с этим репозиторием, в ../food-delivery-<сервис>
```

Контракты сервисы берут из GitHub Packages, а он требует токен даже для чтения. Один раз
создайте токен с правом `read:packages` и положите в `~/.m2/settings.xml` (шаблон — в README
`food-delivery-contracts`). Менять сами контракты и собирать с ними сервис локально можно так:
в `food-delivery-contracts` — `./mvnw install`, версию в pom сервиса поставьте `1.0.0-SNAPSHOT`.

Инфраструктура в Docker, сервисы — из IDE:

```bash
docker compose up -d
```

Дальше запускаются нужные сервисы. Адреса по умолчанию в их `application.yml` рассчитаны
ровно на этот режим: база на `localhost:5432`, Kafka на `localhost:9094` — внешний листенер
брокера. Порты у каждого свои, чтобы сервисы уживались на одном localhost:

| Сервис | Класс запуска | API | Actuator |
|---|---|---|---|
| api-gateway | `ApiGatewayApplication` | 8080 | 9080 |
| insights-service | `InsightsServiceApplication` | 8082 | 9082 |
| notification-service | `NotificationServiceApplication` | 8083 | 9083 |
| catalog-service | `CatalogServiceApplication` | 8084 | 9084 |
| identity-service | `IdentityServiceApplication` | 8085 | 9085 |
| order-service | `OrderServiceApplication` | 8086 | 9086 |
| payment-service | `PaymentServiceApplication` | 8087 | 9087 |
| tracking-service | `TrackingServiceApplication` | 8088 | 9088 |

gRPC: каталог слушает 7084, identity-service — 7085, order-service — 7086, и по умолчанию
сервисы ищут друг друга именно там. JWKS для проверки токенов все берут у identity-service:
`http://localhost:8085/.well-known/jwks.json`. Шлюз не обязателен: сервисы доступны и напрямую,
по своим портам. А вот identity-service нужен всем: без него не войти и не проверить токен.

А вот учётные данные значений по умолчанию не имеют, и `.env` сервисы сами не читают —
это файл для Compose. При запуске из IDE те же переменные задаются в конфигурации запуска:

| Переменная | Кому и когда |
|---|---|
| `POSTGRES_USER`, `POSTGRES_PASSWORD` | только compose: суперпользователь PostgreSQL и перенос данных из старой базы монолита |
| `JWT_PRIVATE_KEY`, `JWT_KEY_ID` | только identity-service, всегда: закрытый ключ подписи токенов |
| `IDENTITY_DB_USER`, `IDENTITY_DB_PASSWORD` | identity-service, всегда |
| `NOTIFICATION_DB_USER`, `NOTIFICATION_DB_PASSWORD` | notification-service, всегда |
| `CATALOG_DB_USER`, `CATALOG_DB_PASSWORD` | catalog-service, всегда |
| `ORDER_DB_USER`, `ORDER_DB_PASSWORD` | order-service, всегда |
| `PAYMENT_DB_USER`, `PAYMENT_DB_PASSWORD` | payment-service, всегда |
| `RABBITMQ_USER`, `RABBITMQ_PASSWORD` | notification-service, всегда; tracking-service — при `TRACKING_RELAY_ENABLED=true` |
| `NEO4J_USERNAME`, `NEO4J_PASSWORD` | при `STORE_NEO4J_ENABLED=true` |
| `CLICKHOUSE_USER`, `CLICKHOUSE_PASSWORD` | при `STORE_CLICKHOUSE_ENABLED=true` |
| `APP_ADMIN_EMAIL`, `APP_ADMIN_PASSWORD` | identity-service, если нужен администратор |

Тестам эти переменные задавать не нужно: их значения лежат в
`src/test/resources/application.properties` каждого сервиса, а адреса и пароли контейнеров
подставляют Testcontainers.

### Тесты

Команды запускаются в репозитории сервиса. Два круга, и разделены они намеренно:

```bash
./mvnw test      # быстрый круг: без Docker, сами тесты — меньше секунды
./mvnw verify    # + интеграционные на Testcontainers, около двух минут
```

Surefire гоняет классы `*Test` — доменные правила и обработчик ошибок. Failsafe гоняет `*IT`
на настоящих контейнерах: именно они проверяют SQL, транзакции и кэш.

Обратите внимание на имена: surefire забирает не только `*Test.java`, но и `Test*.java`,
поэтому интеграционный тест нельзя называть `TestSomethingIT` — он попадёт в быстрый круг
и утащит туда контейнеры.

Перед коммитом нужен `verify`, во время работы достаточно `test`.

Тесты пяти дополнительных хранилищ поднимают ещё пять контейнеров и живут в отдельном
контексте — наследники `AbstractStoresIntegrationTest`. Отдельный он потому, что контекст
Spring кэшируется по набору настроек: попади эти контейнеры в общую конфигурацию, их
поднимал бы каждый интеграционный тест проекта, включая те, что проверяют SQL и ничего
не знают ни о каком MongoDB. Так они стартуют один раз на всю сборку и добавляют к ней
несколько минут, из которых большая часть — старт Cassandra.

## Микросервисы

Переезд шёл по шаблону strangler fig: сервисы выносились из монолита по одному, а сам
монолит продолжал работать и обслуживать всё, что ещё не вынесено. Клиент этого не замечал —
он ходит в шлюз, и вынос модуля не поменял для него ни одного URL. На шестом этапе последние
три модуля монолита стали insights-service, и монолит исчез.

```
                                         ┌───────────────┐
  клиент ───────────────────────────────▶│  api-gateway  │ :8080
                                         └───────┬───────┘
  /notifications  /auth, /admin/users  │ корзина, заказы,     │ GET платежи  │ /restaurants, /search
       │                │              │ доставки, POST оплата │              │        │ отзывы, аналитика,
       ▼                ▼              ▼                       ▼              ▼        ▼ трек, рекомендации
┌──────────────┐ ┌──────────┐  ┌───────────────┐  Kafka   ┌─────────┐  ┌─────────┐  ┌──────────────────┐
│ notification │ │ identity │◀─│ order-service │─команды─▶│ payment │  │ catalog │  │ insights-service │
└──────▲───────┘ └────▲─────┘  │  (оркестратор │◀─исходы──│ service │  └────▲────┘  └────────┬─────────┘
       │              │ gRPC   │     саги)     │──gRPC: ресторан, блюдо──────┘              │
       │              └────────┤               │◀──gRPC: заказы и доставки──────────────────┤
       │                       └───────┬───────┘                                            │
       └──────────── Kafka: order-events (outbox) ─────────────────────────────────────────▶┘ (аналитика)
```

Синхронные вызовы — gRPC, и у каждого свой хозяин данных:

| Кто спрашивает | Кого | Что | Почему не копия |
|---|---|---|---|
| корзина (order-service) | каталог | открыт ли ресторан, блюдо с ценой | цена и наличие меняются, копия устареет |
| каталог, order-service, insights-service | identity-service | управляет ли пользователь рестораном; назначить управляющего | права принадлежат пользователю; копии прав расходятся |
| insights-service | order-service | заказ с позициями; заказы пачкой для графа | отзыв и рекомендации читают заказ, но не владеют им |
| tracking-service | order-service | чей заказ, чья доставка и в каком она статусе | трек пишется только курьером доставки и только в пути |
| insights-service | каталог | название и город ресторана в любом статусе | для GraphQL: экран ресторана рядом с рейтингом и отзывами |

Токены выпускает только identity-service: подписывает закрытым RSA-ключом (RS256) и публикует
открытый в `/.well-known/jwks.json`. Остальные сервисы скачивают JWKS сами, кэшируют
и перечитывают на незнакомый `kid` — поэтому ключ можно сменить без их перезапуска.

Пути `/restaurants/{id}/reviews` и `/analytics` принадлежат insights-service, а `/restaurants/{id}/orders` —
у сервиса заказов: рестораном их делает только префикс. Шлюз уводит их по владельцам раньше,
чем каталожный маршрут `/restaurants/**`. Так же под `/customers/{id}/orders/{id}` трек уходит в сервис трека, отзыв — в insights-service,
а всё остальное о заказе — у сервиса заказов. Путь
`/customers/{id}/orders/{id}/payments` делят двое: `POST` (запустить оплату) — сервис заказов,
`GET` (список платежей) — сервис платежей.

### Живой трек курьера

Клиенту не нужно опрашивать сервер, чтобы видеть курьера на карте. Он открывает одно
WebSocket-соединение и подписывается на свой заказ — точки приходят в момент записи.

```
курьер: POST .../deliveries/{id}/positions ─▶ tracking-service ─▶ Cassandra (трек)
                                                       │
                                                       └─▶ RabbitMQ (STOMP, amq.topic, order.42.track)
                                                                   │
клиент: ws://.../ws/tracking ─ CONNECT (Bearer) ─ SUBSCRIBE /topic/order.42.track ◀─┘
```

- **Протокол — STOMP поверх WebSocket.** Голый WebSocket — канал без адресов; STOMP добавляет
  подписки, заголовки и кадры ошибок. Подключение — `ws://localhost:8080/ws/tracking` через шлюз
  (маршрут со схемой `ws://`), подписка — `/topic/order.{orderId}.track`, в кадре — та же
  точка, что отдаёт `GET .../track`.
- **Токен — в кадре CONNECT.** Браузер не умеет добавлять заголовки к рукопожатию WebSocket,
  а токен в адресе осел бы в логах. Поэтому рукопожатие открыто, а `Authorization: Bearer ...`
  приходит заголовком кадра CONNECT и проверяется тем же декодером JWKS, что и REST.
- **Подписка — только на свой заказ.** Каждая подписка проверяется вопросом к сервису заказов:
  чей это заказ. Чужой заказ — кадр ERROR и закрытое соединение; кадр SEND от клиента
  отклоняется — двигать курьера по карте может только курьер, через REST.
- **Рассылку делает RabbitMQ.** Сервис пересылает кадры в STOMP-плагин брокера (порт 61613),
  и подписки работают при любом числе экземпляров сервиса. Без брокера (`TRACKING_RELAY_ENABLED=false`,
  так по умолчанию при запуске из IDE) работает встроенный брокер в памяти — для одного экземпляра.
- **Живой канал — ускорение, а не источник правды.** Точка сначала записывается в Cassandra,
  потом рассылается; неудачная рассылка не ломает запись.

### Рассылка уведомлений через RabbitMQ

Kafka и RabbitMQ в проекте делят работу, а не дублируют друг друга. Kafka — журнал событий:
«заказ оплачен» хранится, перечитывается, его независимо читают уведомления и аналитика.
RabbitMQ — очереди задач: «отправь письмо» нужно выполнить один раз, с паузой между
попытками и с пределом, а это ровно то, что брокер очередей умеет сам.

```
order-events (Kafka) ─▶ notification-service: запись PENDING ─commit─▶ notifications.dispatch
                                                                          │ email / sms / push
                    notifications.<канал> ◀───────────────────────────────┘
                          │ отказ: попытки ещё есть          ▲ TTL очереди ожидания истёк
                          ▼                                  │
                    notifications.retry ─▶ notifications.<канал>.retry
                          │ попытки кончились
                          ▼
                    FAILED в базе + копия задачи в notifications.dead
```

- **Очередь на канал.** У почты, SMS и пушей разные провайдеры и лимиты. Лёг SMS-шлюз —
  копятся только SMS. Скорость канала задают `prefetch` и число обработчиков.
- **Повтор — свойство очереди.** Отклонённая задача по dead-letter exchange уходит в очередь
  ожидания, по истечении её TTL (`NOTIFICATION_RETRY_DELAY`, 10 с) возвращается обратно.
  Число попыток брокер записывает в заголовок `x-death`; после `NOTIFICATION_MAX_ATTEMPTS`
  уведомление помечается FAILED с причиной, а задача ложится в `notifications.dead`.
- **Приоритеты.** Очереди объявлены с `x-max-priority`: «заказ отменён» обгоняет обычные
  уведомления, накопившиеся перед ним.
- **База — источник правды, очередь — толчок.** Задача публикуется после коммита и с
  подтверждением брокера. Потерянная задача не теряет уведомление: страховочный опрос раз
  в минуту находит застрявшие в PENDING и ставит задачу заново. Повтор задачи безвреден —
  отправка идёт под блокировкой строки и только для PENDING.

Раньше рассылка была опросом базы раз в 30 секунд; теперь письмо уходит сразу после коммита.

### Сага оплаты

Заказ и деньги живут в разных сервисах и разных базах — общей транзакции у них нет.
Оплата поэтому — сага, и сервис заказов в ней оркестратор:

```
клиент: POST .../payments        ─▶ CREATED → PAYMENT_PENDING, в outbox команда PAYMENT_REQUESTED   (202)
payment-service: списал деньги   ─▶ событие PAYMENT_SUCCEEDED  ─▶ PAYMENT_PENDING → PAID
payment-service: банк отказал    ─▶ событие PAYMENT_FAILED     ─▶ PAYMENT_PENDING → CANCELED
клиент отменил PAYMENT_PENDING/PAID                            ─▶ CANCELED, команда REFUND_REQUESTED
payment-service: вернул деньги   ─▶ событие PAYMENT_REFUNDED   ─▶ ORDER_REFUNDED в истории заказа
не дождался оплаты (PAYMENT_TIMEOUT, 15 мин)                   ─▶ CANCELED (+ REFUND_REQUESTED, если оплату запросили)
```

**Почта.** Уведомления по каналу EMAIL уходят настоящими письмами: notification-service берёт адрес
получателя у identity-service по gRPC (в событии заказа адреса нет — это персональные данные) и
отправляет по SMTP. Локально письма принимает Mailpit и показывает на http://localhost:8025, наружу
ничего не уходит. `EMAIL_ENABLED=false` возвращает отправку «в лог». Подробности — в README
[food-delivery-notification-service](https://github.com/Dima77726/food-delivery-notification-service#доставка-по-e-mail).

**Фото блюд.** Менеджер ресторана загружает фото блюда (`PUT /api/v1/restaurants/{id}/menu/items/{itemId}/image`,
JPEG/PNG/WebP до 2 МБ), каталог кладёт его в MinIO и отдаёт в меню `imageUrl` вида `/media/...`; шлюз
читает такие адреса прямо из бакета (только GET/HEAD, без токенов). Ключи — `MINIO_ROOT_USER` и
`MINIO_ROOT_PASSWORD` в `.env`, консоль — http://localhost:9001. Официальные образы `minio/minio` сняты с
публикации, поэтому используется сборка Chainguard.

**Telegram.** Второй настоящий канал: пользователь получает ссылку (`POST /api/v1/notifications/telegram/link`),
открывает её в Telegram — и уведомления о заказах приходят ему и в чат. Нужен бот от @BotFather
(`TELEGRAM_ENABLED=true`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME`); без него канал выключен и
ничего не требует. Устройство, безопасность и ограничения — в README
[food-delivery-notification-service](https://github.com/Dima77726/food-delivery-notification-service#уведомления-в-telegram).

**Платёжный шлюз.** По умолчанию деньги двигает заглушка (`PAYMENT_GATEWAY=simulated`: любое
списание проходит, сумма с копейками `.13` — отказ банка). С `PAYMENT_GATEWAY=stripe` и тестовым
ключом `STRIPE_API_KEY=sk_test_…` payment-service работает с настоящим Stripe в тестовом режиме:
`PaymentIntent` и возвраты, ключ идемпотентности в каждом запросе. Сценарии Postman работают с
обоими. Подробности, ограничения и что делать для боевой оплаты — в README
[food-delivery-payment-service](https://github.com/Dima77726/food-delivery-payment-service#платёжный-шлюз).

- **Топики** — `food-delivery.payment-commands` (пишет только сервис заказов) и
  `food-delivery.payment-events` (пишет только сервис платежей). Ключ — идентификатор заказа,
  поэтому «спиши» и «верни» одного заказа приходят по порядку. Контракты —
  `PaymentCommand` и `PaymentEvent` в `libs/event-contracts`.
- **Outbox с обеих сторон.** Смена статуса заказа и команда, платёж и его исход записываются
  в одной транзакции и уходят в Kafka публикатором outbox.
- **Inbox с обеих сторон.** Kafka доставляет «хотя бы один раз», поэтому идентификатор
  каждого обработанного сообщения записывается в `processed_message` той же транзакцией.
  Повтор ничего не делает: деньги не списываются дважды, заказ не двигается дважды.
- **Компенсация вместо отката.** Отмена оплаченного заказа не «откатывает» платёж, а просит
  вернуть деньги. Команда на возврат уходит и при отмене во время списания: что уже списано,
  знает только сервис платежей, и вернёт он ровно это.
- **Опоздавший исход — норма.** «Оплата прошла» для уже отменённого заказа ничего не меняет:
  возврат запрошен при отмене и выполнится после списания.
- **Ответ клиенту — 202 и PAYMENT_PENDING.** Исход виден в статусе заказа и в
  `GET .../payments`. Держать HTTP-запрос до ответа другого сервиса значило бы вернуть
  синхронную связь, от которой сага избавляет.

| Сервис | Что это |
|---|---|
| `api-gateway` | Spring Cloud Gateway (WebFlux): маршруты, сквозная метка запроса, срез `X-User-Id`, 503 на недоступный сервис |
| `insights-service` | отзывы, аналитика, рекомендации, сводный журнал аудита; REST и GraphQL — то, что осталось от монолита |
| `identity-service` | пользователи, вход, роли, права на рестораны; единственный, кто выпускает JWT |
| `notification-service` | уведомления: потребитель `order-events`, рассылка через очереди RabbitMQ, своя база, `GET /api/v1/notifications/me` |
| `catalog-service` | рестораны, меню, поиск: REST наружу, gRPC внутрь; своя база, кэш в Redis, Elasticsearch |
| `order-service` | корзина, заказ, доставка; журнал аудита заказов (пишет, наружу не отдаёт); оркестратор саги оплаты; gRPC-чтение заказов для insights-service и трека |
| `payment-service` | платежи: списания и возвраты по командам саги; наружу — только чтение платежей |
| `tracking-service` | трек курьера: точки в Cassandra по REST, живой трек по WebSocket (STOMP через RabbitMQ) |

Контракты (`event-contracts`, `grpc-contracts`, клиент REST) — в репозитории
[food-delivery-contracts](https://github.com/Dima77726/food-delivery-contracts).

Правила, которые держат границы:

- **Database-per-service.** У каждого сервиса своя база и своя учётная запись без доступа
  к чужим базам. Локально все базы живут в одном контейнере PostgreSQL, их создаёт
  одноразовый `postgres-provision` при каждом `docker compose up`. В продакшене база
  переезжает на свой сервер сменой одного URL.
- **Общий код — только контракты.** `event-contracts` — формы сообщений и имена
  топиков, `grpc-contracts` — `.proto` синхронных вызовов. Логики в них нет. Общая библиотека с логикой превратила бы
  сервисы в распределённый монолит, который релизится только целиком.
- **Каждый сервис проверяет токен сам.** Шлюз токен не проверяет: внутри сети до сервиса
  можно достучаться и в обход шлюза. Подпись асимметричная (RS256): закрытый ключ есть только
  у identity-service, остальные проверяют открытым и выпустить токен не могут.
- **DLT принадлежит потребителю.** У notification-service свой топик ошибок
  `food-delivery.order-events.notification-service.DLT`, у сервиса заказов —
  `food-delivery.payment-events.DLT`, у сервиса платежей — `food-delivery.payment-commands.DLT`.
- **Сервисы узнают друг друга по сертификатам.** gRPC идёт по взаимному TLS: обе стороны
  предъявляют сертификаты своего CA, имя сервиса записано в CN, и сервер пускает только
  тех, кому вызов положен. `CatalogService` — сервису заказов и insights-service, `RestaurantAccessService` —
  insights-service, каталогу и сервису заказов, `OrderQueryService` — insights-service и сервису трека. Посторонний с настоящим сертификатом получает `PERMISSION_DENIED`.
  Сертификаты выпускает одноразовый `grpc-certs` в том `food_delivery_grpc_certs`;
  включается это профилем `grpc-tls`, который в compose задан всем сервисам с gRPC.
  При запуске из IDE профиль выключен и gRPC открыт — об этом пишется предупреждение.
- **У каждого синхронного вызова дедлайн.** По умолчанию у gRPC-вызова ожидание бесконечно.
  Недоступный сосед — это 503 с советом повторить, а не 500 и не 403.
- **Ссылки между сервисами — без внешних ключей.** Корзина и заказ хранят идентификаторы
  ресторанов и блюд, но не ссылаются на них констрейнтом: таблицы в другой базе. Название
  и цена блюда копируются в корзину в момент добавления — это снимок, а не ссылка.

Notification-service унаследовал от монолита группу потребителей
`food-delivery-notifications` вместе с её офсетами: он продолжил чтение ровно с того
места, где остановился потребитель в монолите, и не разослал уведомления повторно. Так же
insights-service унаследовал группу аналитики `food-delivery-analytics`.

### Перенос данных

Каждый вынос сервиса шёл в два релиза — так, как делают с живыми данными:

1. **Перенос.** Новый сервис получал свою базу, одноразовая задача копировала туда данные
   из базы монолита с сохранением идентификаторов (на них ссылаются заказы и корзины),
   и монолит переставал читать и писать старые таблицы.
2. **Удаление.** Следующим релизом старые таблицы удалялись миграцией монолита
   (`029-drop-moved-tables`). Не в том же релизе — иначе откатываться было бы не к чему.

Каталог и пользователи прошли оба шага: их скрипты переноса удалены вместе со старыми
таблицами и остались в истории git. Заказы и платежи сейчас между шагами: таблицы ещё лежат
в базе монолита, их никто больше не читает, а перенести их в базы сервисов можно так:

```bash
docker compose --profile full stop order-service payment-service
docker compose --profile full up orders-data-migration
docker compose --profile full up -d
```

Перенос (`docker/migrations/orders-from-monolith.sh`) пишет только в пустые базы, сохраняет
идентификаторы и переносит неотправленные события outbox; повторный запуск безопасен.
В новом окружении демо-витрину создаёт миграция каталога `002-seed-demo-catalog`, и только
если каталог пуст.

### Сводный журнал аудита

Действие и запись о нём обязаны фиксироваться в одной транзакции, поэтому журнал пишет тот
сервис, где действие произошло: заказы — order-service, администрирование пользователей —
identity-service, каждый в таблицу `audit_log` своей базы. Читает администратор один журнал
на всех — `GET /api/v1/admin/audit` в insights-service.

```
order-service    ─┐  audit_log (outbox)                      ┌─ ClickHouse audit_log
                  ├─ FOR UPDATE SKIP LOCKED → food-delivery. ─┤  ReplacingMergeTree
identity-service ─┘  отметка published_at     audit-events    └─ GET /api/v1/admin/audit
```

- **Таблица журнала и есть outbox.** Отдельной очереди нет: запись уже легла вместе
  с действием, ей не хватает только отметки `published_at`. Публикатор раз в несколько
  секунд берёт пачку без отметки, отправляет её в топик с ключом по ресурсу (`ORDER:42`,
  `USER:7`) и отмечает то, что Kafka подтвердила. Записи, сделанные до появления отметки,
  уехали первыми — история перенеслась сама.
- **Повтор узнаётся по `eventId`.** Он выводится из пары «сервис — номер записи», поэтому
  у повторной отправки тот же. В ClickHouse копии схлопывает `ReplacingMergeTree`, а пока
  слияние не прошло — `FINAL` при чтении.
- **Журнал не теряется, пока ClickHouse лежит.** Потребитель не отправляет пачку в DLT,
  а повторяет её, пока хранилище не вернётся; офсет всё это время стоит. Записи ждут в топике
  и, в любом случае, в журналах сервисов.
- **Журнал включается вместе с ClickHouse** (`STORE_CLICKHOUSE_ENABLED=true`). Пока он
  выключен, маршрута нет, а записи копятся в топике. Если они пролежат там дольше срока
  хранения топика, их можно отправить заново, сбросив `published_at` в базе источника.
- **Наблюдаемость** — `food_delivery_audit_backlog` в обоих сервисах-источниках: сколько
  записей ещё не уехало. Тревожит рост, а не ненулевое значение.

Фильтры: `service` (`order-service`, `identity-service`), `resourceType` и `resourceId`,
`actorId`, `limit` (до 500). Свежие записи сверху.

### GraphQL в insights-service

Экрану ресторана нужны данные из четырёх мест: название — из каталога, рейтинг и отзывы —
из MongoDB, популярные блюда — из графа Neo4j, продажи (управляющему) — из ClickHouse.
По REST это четыре запроса с фиксированными ответами; в GraphQL — один, и в ответе ровно
те поля, что запросил экран:

```graphql
{
  restaurant(id: 3) {
    name
    city
    rating { average total topTags { tag count } }
    reviews(size: 5) { totalElements items { rating comment createdAt } }
    popularDishes(limit: 3) { name score }
  }
}
```

- **Незапрошенное не вычисляется.** У каждого поля свой обработчик, и вызывается он, только
  если поле в запросе: без `popularDishes` запрос не идёт в Neo4j, без `sales` — в ClickHouse.
- **Права — на полях.** Вход `/graphql` открыт: рейтинг и отзывы публичны. `sales` требует
  управляющего ресторана, `myRecommendations` — вошедшего пользователя. Токен — тем же
  заголовком `Authorization`, что и в REST.
- **Ошибка поля не роняет ответ.** Поля из других хранилищ объявлены nullable: отказ в правах
  на `sales` или выключенный модуль отзывов дают `null` и запись в `errors` с типом
  (`UNAUTHORIZED`, `FORBIDDEN`, `NOT_FOUND`), а остальные поля приходят как обычно.
- **Предел глубины** (`GRAPHQL_MAX_DEPTH`, 6): слишком глубокий запрос отклоняется до выполнения.
- Схема — `insights-service/src/main/resources/graphql/insights.graphqls`, текстом — `GET /graphql/schema`,
  песочница — `/graphiql`.

REST insights-service остался прежним: GraphQL добавлен рядом, а не вместо.

## Устройство модулей

Модули разделены по предметной области, а не по слоям. Рестораны, меню и поиск уехали
в catalog-service, пользователи — в identity-service, уведомления — в notification-service,
корзина, заказ, доставка и аудит заказов — в order-service, оплата — в payment-service.
Трек курьера уехал в tracking-service. Последние три модуля монолита стали insights-service:

```
insights-service/src/main/java/com/dima/fooddelivery/
├── graphql/       схема и резолверы GraphQL
├── catalog/       gRPC-клиент к каталогу
├── order/         gRPC-клиент к сервису заказов
│
├── review/        отзывы о заказах            → MongoDB
├── recommendation/рекомендации по графу       → Neo4j
├── analytics/     витрина продаж и воронка    → ClickHouse
├── audit/         сводный журнал аудита       → ClickHouse
│
└── common/        безопасность, Kafka, метрики, обработка ошибок, хранилища
```

Внутри модуля — четыре слоя: `api` (контроллеры и мапперы), `domain` (типы предметной
области), `persistence` (доступ к данным), `service` (логика).

Модули не лезут в чужие таблицы — тем более в чужие базы. Корзина спрашивает цену блюда
у каталога, отзыв проверяет заказ у сервиса заказов — по gRPC, через интерфейсы
`CatalogClient` и `OrderClient`. Правило живёт в одном месте и меняется в одном месте.

### Четыре подхода к доступу к данным

Это осознанный разнобой, а не наследие: одна кодовая база показывает четыре способа
работать с базой и цену каждого.

| Модуль | Подход | Что на нём видно |
|---|---|---|
| `restaurant` (catalog-service) | Spring Data JPA | derived-запросы; грязная проверка вместо UPDATE |
| `menu` (catalog-service) | Spring Data JPA | `@OneToMany`, cascade, `orphanRemoval`, `LEFT JOIN FETCH` против N+1 |
| `user` (identity-service) | Hibernate вручную | `EntityManager`, JPQL, `@ElementCollection` для ролей |
| `payment` (payment-service) | Hibernate вручную | Criteria API; массовое обновление в обход контекста |
| `order`, `cart`, `delivery` (order-service) | Spring JDBC | рукописный SQL, `RowMapper`, `FOR UPDATE SKIP LOCKED` |
| `audit` (order-service) | голый JDBC | `Connection`, `PreparedStatement`, ручной разбор строк |

Внутри одного сервиса все подходы работают поверх одного `DataSource` и одного менеджера транзакций
(`JpaTransactionManager`): `JdbcTemplate` берёт соединение через `DataSourceUtils`
и попадает в ту же транзакцию, что и `EntityManager`.

### Шесть хранилищ и зачем каждое

PostgreSQL остаётся системой записи. Всё остальное — либо производные проекции, которые
можно потерять и построить заново, либо данные, которым реляционная модель не нужна.

| Хранилище | Модуль | Задача | Почему именно оно |
|---|---|---|---|
| PostgreSQL | все сервисы, у каждого своя база | заказы, деньги, пользователи, каталог | транзакции и целостность |
| Redis | catalog-service | кэш витрины | скорость чтения |
| Kafka | order-service → notification-service, `analytics`; сага order ⇄ payment; журналы аудита → `audit` | события заказа, команды и исходы оплаты, записи аудита | независимые потребители, асинхронная сага |
| RabbitMQ | notification-service, tracking-service | очереди отправки по каналам; рассылка живого трека по STOMP | повтор через TTL и DLX, приоритеты; подписки WebSocket, общие для всех экземпляров |
| MongoDB | `review` | отзывы с оценками блюд и метками | подвижная схема, вложенные документы |
| Cassandra | tracking-service | координаты курьера | поток вставок, чтение по одному ключу, TTL |
| Neo4j | `recommendation` | «с этим заказывают» | обход графа на два шага |
| ClickHouse | `analytics`, `audit` | продажи по дням, воронка статусов; сводный журнал аудита | агрегаты по колонкам; журнал, который только растёт |
| Elasticsearch | catalog-service, `search` | поиск с морфологией и опечатками | разбор текста |

Способ доступа у каждого свой, и это продолжение того же осознанного разнобоя:

| Модуль | Подход | Что на нём видно |
|---|---|---|
| `review` | Spring Data MongoDB | репозитории; `$facet` в aggregation pipeline |
| `search` | Spring Data Elasticsearch | `ElasticsearchOperations`, Query DSL, `multi_match` с нечёткостью |
| `tracking` (tracking-service) | голый драйвер DataStax | CQL руками, подготовленные запросы, `timeuuid` как ключ |
| `recommendation` | голый драйвер Neo4j | Cypher руками, `MERGE` ради идемпотентности |
| `analytics` | `JdbcTemplate` поверх своего пула | SQL руками, пакетная вставка, `ReplacingMergeTree` |
| `audit` (insights-service) | тот же пул | `FINAL` вместо агрегатов: журнал отвечает строками, а не суммами |

У Cassandra и Neo4j взяты драйверы, а не стартеры Spring Boot, и на это есть причины,
описанные в `CassandraConfig` и `Neo4jConfig`: стартер Cassandra открывает соединение
на старте контекста, а Spring Data Neo4j добавляет второй менеджер транзакций рядом
с `JpaTransactionManager`. ClickHouse не получает бина `DataSource` намеренно — второй
такой бин выключил бы автоконфигурацию основного пула; подробности в `ClickHouseJdbc`.

### Как данные попадают в производные хранилища

Три модуля из пяти работают с копиями — и сводный журнал аудита вместе с ними, — и каждый
получает их по-своему. Разница не случайна: она следует из того, что нужно потребителю.

| Куда | Как | Почему так |
|---|---|---|
| ClickHouse | потребители Kafka, у витрины и журнала аудита свои группы | событие уже содержит всё, что нужно витрине и журналу |
| Neo4j | циклическая сверка заказов пачками с курсором (gRPC к order-service) | учитывает состав заказа, отмены и поздние коммиты |
| Elasticsearch | полная переиндексация по расписанию | двойная запись оставила бы индекс расходящимся навсегда |

Отзывы в MongoDB и трек в Cassandra — единственные данные вне PostgreSQL, у которых нет
второго источника: их пишет сразу API, и восстановить их неоткуда.

Граф после конца выборки возвращает курсор к началу. Связи каждого заказа заменяются
атомарно; отменённый заказ удаляет свои прежние связи. Поэтому задержка изменения графа
зависит от длины полного прохода: примерно `(число пачек + 1) × интервал`, плюс время
обработки. Синхронизация ручного запуска, таймера и перестроения действует внутри одного
экземпляра приложения. Для большого объёма истории следующим шагом будет очередь изменений.

В отзыве можно оценить только блюда из доставленного заказа, каждое один раз. Название
сервер берёт из позиции заказа; присланное клиентом название не меняет сохранённый снимок.

Подробности каждого решения — в javadoc соответствующих репозиториев. Отправная точка —
`AuditLogRepository` в order-service: там же объяснено, почему голый JDBC обязан брать соединение
у `DataSourceUtils`, а не у `DataSource`.

### База данных

Схемой владеет Liquibase, и только он. Hibernate работает с `ddl-auto: validate` —
сверяет сущности с таблицами на старте и падает при расхождении, но ничего не меняет.

Миграции лежат в `src/main/resources/db/changelog/migrations/` каждого сервиса, каждая
ссылается на файл с SQL. У вынесенных сервисов таблицы в схеме `public` своей базы;
старая база монолита (схема `food_app`) осталась только источником для переноса заказов и платежей.

Схему пяти дополнительных хранилищ Liquibase не трогает: у него нет для них диалектов,
да и незачем. Таблицу в Cassandra, таблицу в ClickHouse, индексы MongoDB и индексы
Elasticsearch создают на старте отдельные классы — `CourierTrackSchema`,
`OrderAnalyticsSchema`, `ReviewIndexes` и `SearchIndex`. Это осознанное упрощение,
допустимое ровно потому, что таблиц там по одной, а три из четырёх хранилищ содержат
производные данные: их не мигрируют, а строят заново.

### События и надёжность

Смена статуса заказа пишется в таблицу `order_event_outbox` сервиса заказов в той же транзакции,
что и сам заказ, — туда же ложатся команды сервису платежей. Сервис платежей так же пишет
исходы в свой `payment_outbox`. Отдельная задача в каждом разбирает очередь и отправляет
сообщения в Kafka. Так сообщение не может уехать по откатившейся транзакции, а недоступный
брокер не роняет оформление заказа. Принимающая сторона саги отсеивает повторы по inbox
(`processed_message`).

Продюсер идемпотентный, `acks=all`; необработанные сообщения уходят в DLT — у каждого
потребляющего сервиса свой.

**Предохранитель на gRPC.** У исходящих вызовов есть дедлайн, но он ограничивает одно
ожидание, а не их число: пока сосед лежит, каждый запрос ждёт свои две секунды, держит поток
и соединение с базой, и пул кончается за секунды. Клиентский интерцептор
`CircuitBreakerClientInterceptor` (Resilience4j; order, insights, catalog, tracking) после
нескольких подряд неудач размыкается и несколько секунд отвечает отказом сразу, потом
пропускает пробные вызовы. Отказом служит статус `UNAVAILABLE`, который клиенты и так переводят
в 503, — их код не менялся. Неудачей считается только нездоровье соседа (`UNAVAILABLE`,
`DEADLINE_EXCEEDED`, `INTERNAL`…): `NOT_FOUND` и `FAILED_PRECONDITION` — нормальные ответы
исправного каталога и предохранитель не размыкают. Повторов нет: вызов синхронный, повтор
к недоступному соседу только удвоил бы ожидание. Пороги — `app.grpc.circuit-breaker.*`.

**Ограничение частоты на шлюзе.** Корзина токенов в Redis на каждый адрес клиента, счёт
атомарный (Lua-скрипт) и общий для всех экземпляров шлюза. Два ведра: общее (по умолчанию
50 запросов в секунду, всплеск 100) и строгое на `/api/v1/auth/**` — примерно пять попыток
подряд, потом одна в четыре секунды: это перебор паролей, а не обычный трафик. Превышение — 429
с `Retry-After`. Недоступный Redis ограничитель пропускает: потеря лимита лучше потери входа.
Флаг `RATE_LIMIT_ENABLED` (в compose включён, в тестах и при запуске из IDE нет — шлюзу тогда
не нужен Redis). Ключ — адрес соединения, `X-Forwarded-For` не читается: он подделывается одной
строкой. Побочное следствие на Docker Desktop: запросы с хоста приходят с одного адреса
шлюза сети Docker, поэтому локально все клиенты делят одно ведро.

### Наблюдаемость

Каждый запрос получает `X-Correlation-Id` в шлюзе (или использует присланный) и возвращает
его в ответе. Метка едет заголовком в сервис, оттуда метаданными gRPC в соседние сервисы
(`x-correlation-id`) и через outbox и Kafka в потребителей,
попадает в MDC и видна в каждой строке лога каждого сервиса — по ней запрос
прослеживается насквозь:

```bash
docker compose --profile full logs | grep <correlation-id>
```

Метрики отдаёт Actuator в формате Prometheus, дашборд Grafana поставляется в
`observability/grafana/provisioning/`.

**Трассы.** Каждый сервис трассирует запросы через Micrometer Tracing поверх OpenTelemetry
и отправляет спаны по OTLP в Tempo. Заголовок `traceparent` (W3C) идёт через HTTP, gRPC,
Kafka и RabbitMQ, поэтому путь запроса от шлюза до соседнего сервиса — одна трасса.
Служебные запросы (`/actuator/**`) не наблюдаются: их опрашивает Prometheus каждые пять
секунд, и без фильтра они забили бы поиск.

**Логи.** Alloy читает stdout контейнеров через сокет Docker и пишет в Loki; сервисам
об этом знать не нужно. В каждой строке — `[сервис,traceId,spanId,correlationId,userId]`.

В Grafana (http://localhost:3000) оба хранилища подключены как источники и связаны:
в Explore → Loki у строки лога есть ссылка на трассу по `traceId`, а в Tempo у спана — кнопка
«Logs» с логами этого сервиса за окно спана. Поиск по сервису — `{service="order-service"}`.

Экспорт трасс выключен по умолчанию (`TRACING_EXPORT_ENABLED=false`), чтобы запуск из IDE и
тесты не сыпали ошибками о недоступном Tempo; Docker Compose включает его для всех сервисов.
Для запуска из IDE при поднятом стеке достаточно `TRACING_EXPORT_ENABLED=true` — Tempo слушает
`localhost:4318`. Доля трассируемых запросов — `TRACING_SAMPLING_PROBABILITY` (по умолчанию `1.0`,
вне локального стека хватает `0.1`).

**Алерты.** Правила Grafana (`observability/grafana/provisioning/alerting/rules.yml`), без
отдельного Alertmanager: Grafana уже работает и умеет оба источника, включая Loki — по метрикам
не увидеть сообщение, ушедшее в DLT. Что отслеживается: события outbox в `FAILED` и застрявшая
очередь, не уезжающий в сводный журнал аудит, доля 5xx, отказов платежей, заполненная куча,
сервис без метрик, разомкнутый предохранитель gRPC и сообщение в DLT. Состояние — в Alerting →
Alert rules. Куда слать уведомления, не настроено: адреса и токены — секреты, их задают в
Alerting → Contact points. В частичном стеке (без профиля `full`) «сервис без метрик»
сработает для всех, кого не поднимали, — это ожидаемо.

**Где трасса обрывается.** Outbox разрывает её намеренно: событие публикуется планировщиком
в другом потоке и позже, и `traceparent` запроса в outbox пока не сохраняется. Сообщение
Kafka начинает новую трассу, а связывает её с исходной `correlationId` — он едет в заголовке
и виден в логах обеих сторон: `{service=~".+"} |= "<correlation-id>"` в Loki.

## API

Источник истины по контракту — `openapi/food-delivery-api.yaml` в репозитории
`food-delivery-contracts`. Из него генерируется типизированный клиент, а сама спецификация едет
внутри jar клиента: catalog-service распаковывает её оттуда и генерирует интерфейсы своих
контроллеров.

Спецификация описывает рестораны, меню и пять дополнительных модулей: отзывы, трекинг,
рекомендации, аналитику и поиск. Рестораны и меню реализуют сгенерированные интерфейсы;
для дополнительных модулей совместимость проверяется контрактными тестами клиента.
Живой контракт всего API отдаёт springdoc на `/swagger-ui.html`.

Готовая Postman-коллекция на весь API — в `postman/`, там же инструкция.

### Что добавили пять хранилищ

Маршруты появляются вместе с модулем: при выключенном хранилище контроллера нет и ответ
будет 404, а не 500 или пустой список. Так честнее — функциональности в такой сборке
действительно нет.

| Метод и путь | Кто | Что делает |
|---|---|---|
| `POST /api/v1/customers/{id}/orders/{orderId}/review` | клиент | отзыв о доставленном заказе |
| `GET /api/v1/restaurants/{id}/reviews` | все | отзывы постранично |
| `GET /api/v1/restaurants/{id}/reviews/summary` | все | среднее, гистограмма оценок, частые метки |
| `POST /api/v1/couriers/{id}/deliveries/{deliveryId}/positions` | курьер | отправить координату |
| `GET /api/v1/couriers/{id}/deliveries/{deliveryId}/track` | курьер | свой трек |
| `GET /api/v1/customers/{id}/orders/{orderId}/track` | клиент | где мой заказ |
| `GET /api/v1/search?q=&city=` | все | поиск по ресторанам и блюдам |
| `GET /api/v1/customers/{id}/recommendations` | клиент | что берут с похожим вкусом |
| `GET /api/v1/menu-items/{id}/ordered-together` | вошедшие | что заказывают вместе |
| `GET /api/v1/restaurants/{id}/analytics/sales` | владелец | продажи по дням |
| `GET /api/v1/restaurants/{id}/analytics/funnel` | владелец | воронка статусов |
| `GET /api/v1/admin/analytics/sales` | админ | продажи всей платформы |
| `POST /api/v1/admin/search/reindex` | админ | переиндексировать витрину сейчас |
| `POST /api/v1/admin/recommendations/project` | админ | догнать граф на одну пачку |
| `POST /api/v1/admin/recommendations/rebuild` | админ | построить граф заново |

Поиск и отзывы открыты без токена — по тому же признаку, что список ресторанов и меню:
это чтение публичного каталога.

### Аутентификация

JWT на RS256 от identity-service, роли `CUSTOMER`, `RESTAURANT_OWNER`, `COURIER`, `ADMIN`.
В токене — `sub` (идентификатор), `roles` и `email`; e-mail нужен журналам аудита, чтобы
не спрашивать сервис пользователей на каждую запись. Роль `ADMIN` через регистрацию
не выдаётся: первый администратор создаётся при старте identity-service из `APP_ADMIN_EMAIL`
и `APP_ADMIN_PASSWORD`, а если они не заданы — не создаётся вовсе.

Вход и регистрация выдают пару токенов. Access-токен (JWT) живёт 15 минут и проверяется
любым сервисом без обращения к identity-service — поэтому отозвать его нельзя. Refresh-токен —
случайная строка, живёт 30 дней и проверяется только по базе identity-service, поэтому
отзывается сразу:

| Запрос | Что делает |
|---|---|
| `POST /api/v1/auth/refresh` `{"refreshToken": "…"}` | новая пара; старый refresh-токен больше не действует |
| `POST /api/v1/auth/logout` `{"refreshToken": "…"}` | завершает эту сессию, другие устройства остаются |

Refresh-токен одноразовый. Если уже обменянный токен предъявят снова, значит, у него две копии,
и identity-service отзывает всю цепочку: войти заново придётся и владельцу, и тому, кто токен
украл. Блокировка пользователя администратором отзывает все его сессии. В базе хранится
только SHA-256 токена.

## Сборка

Каждый сервис собирается в своём репозитории:

```bash
./mvnw verify           # сборка и все тесты сервиса (интеграционным нужен Docker)
docker build --secret id=maven_settings,src=$HOME/.m2/settings.xml -t food-delivery-order-service .
```

Секрет `maven_settings` — ваш `~/.m2/settings.xml` с токеном для GitHub Packages: контракты
читаются во время сборки образа, и в слои образа токен не попадает.

### CI и поставка

| Репозиторий | Workflow | Когда | Что делает |
|---|---|---|---|
| сервис | `ci.yml` | PR и пуш в `dev`/`main` | сборка и все тесты сервиса, включая интеграционные на Testcontainers |
| сервис | `image.yml` | пуш в `dev`/`main` | образ в GHCR с тегами `<sha>` и `<ветка>` |
| контракты | `ci.yml` | PR и пуш в `main` | сборка контрактов, генерация стабов gRPC и клиента |
| контракты | `contracts.yml` | тег `vX.Y.Z` | публикация в GitHub Packages |
| платформа | `compose.yml` | PR и пуш | проверка, что `docker-compose.yml` разбирается во всех профилях |

**Версии.** У контрактов своя версия (теги `vX.Y.Z` в `food-delivery-contracts`), сервисы
указывают её в `contracts.version`. Совместимое изменение — минорная версия, несовместимое —
мажорная и новый пакет `.proto` (`catalog.v2`). Сервисы поставляются образами, и их версия —
это sha коммита в теге образа.

**Изменить контракт.** Правка в `food-delivery-contracts`, тег новой версии, затем в каждом
затронутом сервисе поднять `contracts.version`. Контракты — единственное общее место, поэтому
порядок обратный монорепо: сначала контракт, потом потребители.

**Готовые образы.** Поднять стек из того, что собрал CI:

```bash
docker login ghcr.io          # если пакеты приватные
IMAGE_TAG=dev docker compose --profile full pull
IMAGE_TAG=dev docker compose --profile full up -d
```

Один сервис можно взять из локальной сборки, остальные оставить готовыми:
`ORDER_SERVICE_TAG=local docker compose --profile full up -d order-service`.
