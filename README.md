# Food Delivery Platform

Платформа доставки еды на Spring Boot 4 и Java 21: рестораны, меню, корзина, заказ,
оплата, доставка, уведомления и журнал аудита. Плюс пять модулей поверх пяти разных
хранилищ — отзывы, трек курьера, аналитика, рекомендации и поиск.

Проект переезжает с модульного монолита на микросервисы — постепенно, по одному сервису
(см. [Микросервисы](#микросервисы)). Сейчас за единым шлюзом работают монолит и два
вынесенных из него сервиса — пользователи, каталог и уведомления. Синхронно сервисы
разговаривают по gRPC, асинхронно — через Kafka.

Проект учебный, но написан по боевым правилам: транзакционный outbox для событий, сквозная
метка запроса, идемпотентная оплата, миграции Liquibase, интеграционные тесты на настоящих
PostgreSQL, Redis и Kafka через Testcontainers.

## Быстрый старт

Нужны Docker и Docker Compose. JDK ставить не обязательно — сборка идёт внутри образа.

```bash
cp .env.example .env
# замените в .env заглушки change-me-* на свои значения, а JWT_PRIVATE_KEY — на ключ:
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 | openssl pkcs8 -topk8 -nocrypt -outform DER | base64 -w0
docker compose --profile full up -d --build
```

Ни одного пароля в репозитории нет: у учётных данных не осталось значений по умолчанию
ни в `application.yml`, ни в `docker-compose.yml`. Незаполненный `.env` — это остановка
на старте с именем недостающей переменной, а не молчаливый запуск под чужим паролем.
Полный список переменных с пояснениями — в [.env.example](.env.example).

Профиль `full` поднимает и сами сервисы: шлюз, монолит, пользователей, каталог и уведомления. Без него
стартует только инфраструктура — это режим для разработки, когда сервисы запускаются из IDE.

| Что | Адрес |
|---|---|
| API (через шлюз) | http://localhost:8080/api/v1 |
| Swagger UI | http://localhost:8080/swagger-ui.html |
| Kafka UI | http://localhost:8090 |
| Prometheus | http://localhost:9090 |
| Grafana | http://localhost:3000 |

Наружу опубликован только шлюз. Монолит и сервисы, как и их служебные порты (8081),
доступны только внутри сети compose: `/actuator/prometheus` и `/actuator/health` видит
Prometheus, а снаружи их не видно.

### Проверить, что всё поднялось

```bash
curl http://localhost:8080/api/v1/restaurants
```

Миграции каталога создают три ресторана с меню, так что список не будет пустым.

### Пять дополнительных хранилищ

MongoDB, Cassandra, Neo4j, ClickHouse и Elasticsearch живут под отдельным профилем
и по умолчанию выключены. Вместе они просят около пяти гигабайт памяти, а нужны только тем
пяти модулям, которые с ними работают, — поэтому обычный `docker compose up -d` их
не поднимает и приложение стартует ровно так же, как стартовало без них.

Включение состоит из двух шагов, и оба обязательны:

```bash
docker compose --profile stores up -d
```

затем в `.env` снять комментарий с нужных строк:

```
STORE_MONGO_ENABLED=true
STORE_CASSANDRA_ENABLED=true
STORE_NEO4J_ENABLED=true
STORE_CLICKHOUSE_ENABLED=true
STORE_ELASTICSEARCH_ENABLED=true
```

Выключатели независимы: можно поднять только MongoDB и включить только отзывы.

Порядок важен. Включённый модуль требует доступного сервера: свою схему он создаёт на старте
и при недоступном хранилище не даёт приложению подняться. Это сделано намеренно — молча
стартовавший сервис с наполовину рабочим API обнаружился бы много позже и по жалобе.

| Что | Адрес |
|---|---|
| Neo4j Browser | http://localhost:7474 |
| Elasticsearch | http://localhost:9200 |
| ClickHouse HTTP | http://localhost:8123 |
| MongoDB | localhost:27017 |
| Cassandra | localhost:9042 |

Neo4j и ClickHouse ходят под учётными записями из `.env` — `NEO4J_USERNAME`/`NEO4J_PASSWORD`
и `CLICKHOUSE_USER`/`CLICKHOUSE_PASSWORD`. Значений по умолчанию у них нет: включённый
модуль без своей переменной останавливает приложение и называет её. Compose передаёт
те же значения контейнерам, при запуске из IDE их нужно задать в конфигурации запуска.

Пользователем ClickHouse нельзя делать `default`: скрипт образа пытается создать уже
существующего пользователя и падает. А без явной учётной записи образ закрывает `default`
сетевой доступ, и приложение получает `Authentication failed` вместо соединения.

В DataGrip: host `localhost`, port `8123`, database `food_delivery`, логин и пароль — из `.env`.

После изменения учётной записи пересоздай контейнер командой
`docker compose --profile stores up -d --no-deps --force-recreate clickhouse`.
Именованный том с данными сохраняется. Healthcheck выполняет `SELECT 1` с аутентификацией:
один `/ping` не проверяет возможность приложения выполнять запросы.

## Разработка

Инфраструктура в Docker, сервисы — из IDE:

```bash
docker compose up -d
```

Дальше запускаются нужные сервисы. Адреса по умолчанию в их `application.yml` рассчитаны
ровно на этот режим: база на `localhost:5432`, Kafka на `localhost:9094` — внешний листенер
брокера. Порты у каждого свои, чтобы сервисы уживались на одном localhost:

| Сервис | Класс запуска | API | Actuator |
|---|---|---|---|
| api-gateway | `ApiGatewayApplication` | 8080 | 9080 |
| монолит (core) | `FoodDeliveryPlatformApplication` | 8082 | 9082 |
| notification-service | `NotificationServiceApplication` | 8083 | 9083 |
| catalog-service | `CatalogServiceApplication` | 8084 | 9084 |
| identity-service | `IdentityServiceApplication` | 8085 | 9085 |

gRPC: каталог слушает 7084, identity-service — 7085, и по умолчанию сервисы ищут друг друга
именно там. JWKS для проверки токенов все берут у identity-service:
`http://localhost:8085/.well-known/jwks.json`. Шлюз не обязателен: сервисы доступны и напрямую,
по своим портам. А вот identity-service нужен всем: без него не войти и не проверить токен.

А вот учётные данные значений по умолчанию не имеют, и `.env` сервисы сами не читают —
это файл для Compose. При запуске из IDE те же переменные задаются в конфигурации запуска:

| Переменная | Кому и когда |
|---|---|
| `POSTGRES_USER`, `POSTGRES_PASSWORD` | монолиту, всегда |
| `JWT_PRIVATE_KEY`, `JWT_KEY_ID` | только identity-service, всегда: закрытый ключ подписи токенов |
| `IDENTITY_DB_USER`, `IDENTITY_DB_PASSWORD` | identity-service, всегда |
| `NOTIFICATION_DB_USER`, `NOTIFICATION_DB_PASSWORD` | notification-service, всегда |
| `CATALOG_DB_USER`, `CATALOG_DB_PASSWORD` | catalog-service, всегда |
| `NEO4J_USERNAME`, `NEO4J_PASSWORD` | при `STORE_NEO4J_ENABLED=true` |
| `CLICKHOUSE_USER`, `CLICKHOUSE_PASSWORD` | при `STORE_CLICKHOUSE_ENABLED=true` |
| `APP_ADMIN_EMAIL`, `APP_ADMIN_PASSWORD` | identity-service, если нужен администратор |

Тестам эти переменные задавать не нужно: их значения лежат в
`src/test/resources/application.properties` каждого модуля, а адреса и пароли контейнеров
подставляют Testcontainers.

### Тесты

Два круга, и разделены они намеренно:

```bash
./mvnw test      # быстрый круг: без Docker, сами тесты — меньше секунды
./mvnw verify    # + интеграционные на Testcontainers, около двух минут
```

Основное время первой команды уходит не на тесты, а на генерацию из OpenAPI
и компиляцию.

Surefire гоняет классы `*Test` — доменные правила и обработчик ошибок. Failsafe гоняет `*IT`
на настоящих контейнерах: именно они проверяют SQL, транзакции и кэш.

Обратите внимание на имена: surefire забирает не только `*Test.java`, но и `Test*.java`,
поэтому интеграционный тест нельзя называть `TestSomethingIT` — он попадёт в быстрый круг
и утащит туда контейнеры.

Перед коммитом нужен `verify`, во время работы достаточно `test`.

Тесты пяти дополнительных хранилищ поднимают ещё пять контейнеров и живут в отдельном
контексте — наследники `AbstractStoresIntegrationTest`. Отдельный он потому, что контекст
Spring кэшируется по набору настроек: попади эти контейнеры в общую конфигурацию, их
поднимал бы каждый интеграционный тест проекта, включая те, что проверяют SQL и ничего
не знают ни о каком MongoDB. Так они стартуют один раз на всю сборку и добавляют к ней
несколько минут, из которых большая часть — старт Cassandra.

## Микросервисы

Переезд идёт по шаблону strangler fig: сервисы выносятся из монолита по одному, а сам
монолит продолжает работать и обслуживать всё, что ещё не вынесено. Клиент этого
не замечает — он ходит в шлюз, и вынос модуля для него не меняет ни одного URL.

```
                                    ┌───────────────┐
  клиент ──────────────────────────▶│  api-gateway  │ :8080
                                    └───────┬───────┘
   /notifications/**   /auth/**, /admin/users/**  │ всё остальное   /restaurants, /search
        ┌──────────────────┬──────────────────────┼─────────────────────────┐
        ▼                  ▼                      ▼                         ▼
┌──────────────┐  ┌──────────────────┐  ┌──────────────────┐  gRPC  ┌─────────────────┐
│ notification │  │ identity-service │  │  core (монолит)  │ ─────▶ │ catalog-service │
└──────┬───────┘  └────────▲─────────┘  └────────┬─────────┘        └────────┬────────┘
       │                   │ gRPC: права на рестораны (от core и catalog)    │
       │ ◀─ Kafka: order-events ─────────────────┤ (outbox)                  │
       ▼                   ▼                     ▼                           ▼
 БД notification     БД identity          БД food_delivery         БД catalog, Redis, ES
```

Синхронные вызовы — gRPC, и у каждого свой хозяин данных:

| Кто спрашивает | Кого | Что | Почему не копия |
|---|---|---|---|
| корзина монолита | каталог | открыт ли ресторан, блюдо с ценой | цена и наличие меняются, копия устареет |
| каталог, монолит | identity-service | управляет ли пользователь рестораном; назначить управляющего | права принадлежат пользователю; копии прав расходятся |

Токены выпускает только identity-service: подписывает закрытым RSA-ключом (RS256) и публикует
открытый в `/.well-known/jwks.json`. Остальные сервисы скачивают JWKS сами, кэшируют
и перечитывают на незнакомый `kid` — поэтому ключ можно сменить без их перезапуска.

Пути `/restaurants/{id}/orders`, `/reviews`, `/analytics` остались у монолита: рестораном
их делает только префикс, а данные — заказы, отзывы, продажи — монолитные. Шлюз уводит
их в монолит раньше, чем каталожный маршрут `/restaurants/**`.

| Модуль | Что это |
|---|---|
| `api-gateway` | Spring Cloud Gateway (WebFlux): маршруты, сквозная метка запроса, срез `X-User-Id`, 503 на недоступный сервис |
| `service` | монолит: корзина, заказ, оплата, доставка, отзывы, аналитика, аудит |
| `identity-service` | пользователи, вход, роли, права на рестораны; единственный, кто выпускает JWT |
| `notification-service` | уведомления: потребитель `order-events`, своя база, `GET /api/v1/notifications/me` |
| `catalog-service` | рестораны, меню, поиск: REST наружу, gRPC внутрь; своя база, кэш в Redis, Elasticsearch |
| `libs/event-contracts` | контракты событий Kafka |
| `libs/grpc-contracts` | `.proto` и сгенерированные из них стабы gRPC |
| `client` | типизированный Java-клиент к API |

Правила, которые держат границы:

- **Database-per-service.** У каждого сервиса своя база и своя учётная запись без доступа
  к чужим базам. Локально все базы живут в одном контейнере PostgreSQL, их создаёт
  одноразовый `postgres-provision` при каждом `docker compose up`. В продакшене база
  переезжает на свой сервер сменой одного URL.
- **Общий код — только контракты.** `libs/event-contracts` — формы сообщений и имена
  топиков, `libs/grpc-contracts` — `.proto` синхронных вызовов. Логики в них нет. Общая библиотека с логикой превратила бы
  сервисы в распределённый монолит, который релизится только целиком.
- **Каждый сервис проверяет токен сам.** Шлюз токен не проверяет: внутри сети до сервиса
  можно достучаться и в обход шлюза. Подпись асимметричная (RS256): закрытый ключ есть только
  у identity-service, остальные проверяют открытым и выпустить токен не могут.
- **DLT принадлежит потребителю.** У notification-service свой топик ошибок
  `food-delivery.order-events.notification-service.DLT`.
- **Сервисы узнают друг друга по сертификатам.** gRPC идёт по взаимному TLS: обе стороны
  предъявляют сертификаты своего CA, имя сервиса записано в CN, и сервер пускает только
  тех, кому вызов положен. `CatalogService` — только монолиту, `RestaurantAccessService` —
  монолиту и каталогу. Посторонний с настоящим сертификатом получает `PERMISSION_DENIED`.
  Сертификаты выпускает одноразовый `grpc-certs` в том `food_delivery_grpc_certs`;
  включается это профилем `grpc-tls`, который в compose задан всем сервисам с gRPC.
  При запуске из IDE профиль выключен и gRPC открыт — об этом пишется предупреждение.
- **У каждого синхронного вызова дедлайн.** По умолчанию у gRPC-вызова ожидание бесконечно.
  Недоступный сосед — это 503 с советом повторить, а не 500 и не 403.
- **Ссылки между сервисами — без внешних ключей.** Корзина и заказ хранят идентификаторы
  ресторанов и блюд, но не ссылаются на них констрейнтом: таблицы в другой базе. Название
  и цена блюда копируются в корзину в момент добавления — это снимок, а не ссылка.

Notification-service унаследовал от монолита группу потребителей
`food-delivery-notifications` вместе с её офсетами: он продолжает чтение ровно с того
места, где остановился потребитель в монолите, и не рассылает уведомления повторно.
Монолит теперь читает топик в группе `food-delivery-core`.

### Перенос данных

Каждый вынос сервиса шёл в два релиза — так, как делают с живыми данными:

1. **Перенос.** Новый сервис получал свою базу, одноразовая задача копировала туда данные
   из базы монолита с сохранением идентификаторов (на них ссылаются заказы и корзины),
   и монолит переставал читать и писать старые таблицы.
2. **Удаление.** Следующим релизом старые таблицы удалялись миграцией монолита
   (`029-drop-moved-tables`). Не в том же релизе — иначе откатываться было бы не к чему.

Скрипты переноса (`docker/migrations/*-from-monolith.sh`) и одноразовые сервисы compose
для них удалены вместе со старыми таблицами — переносить больше нечего. Найти их можно
в истории git. В новом окружении демо-витрину создаёт миграция каталога
`002-seed-demo-catalog`, и только если каталог пуст.

### Что ещё не сделано

- **Аудит в двух местах.** Действия с заказами пишет журнал монолита (`/api/v1/admin/audit`),
  администрирование пользователей — журнал identity-service (таблица `audit_log` его базы).
  Следующий шаг — сводный аудит: сервисы публикуют записи событиями, один потребитель
  собирает их вместе.

## Устройство монолита

Модули разделены по предметной области, а не по слоям.

Рестораны, меню и поиск уехали в catalog-service, пользователи — в identity-service,
уведомления — в notification-service.

```
service/src/main/java/com/dima/fooddelivery/
├── catalog/       gRPC-клиент к каталогу
├── cart/          корзина
├── order/         заказ, его статусы и outbox
├── payment/       оплата и возвраты
├── delivery/      назначение курьера и доставка
├── audit/         журнал действий
├── admin/         журнал аудита для администратора
│
├── review/        отзывы о заказах            → MongoDB
├── tracking/      трек курьера                → Cassandra
├── recommendation/рекомендации по графу       → Neo4j
├── analytics/     витрина продаж и воронка    → ClickHouse
│
└── common/        безопасность, Kafka, метрики, обработка ошибок, хранилища
```

Внутри модуля — четыре слоя: `api` (контроллеры и мапперы), `domain` (типы предметной
области), `persistence` (доступ к данным), `service` (логика).

Модули не лезут в чужие таблицы. Корзина спрашивает цену блюда у `MenuService`, а статус
ресторана — у `RestaurantService`. Правило живёт в одном месте и меняется в одном месте.

### Четыре подхода к доступу к данным

Это осознанный разнобой, а не наследие: одна кодовая база показывает четыре способа
работать с базой и цену каждого.

| Модуль | Подход | Что на нём видно |
|---|---|---|
| `restaurant` (catalog-service) | Spring Data JPA | derived-запросы; грязная проверка вместо UPDATE |
| `menu` (catalog-service) | Spring Data JPA | `@OneToMany`, cascade, `orphanRemoval`, `LEFT JOIN FETCH` против N+1 |
| `user` | Hibernate вручную | `EntityManager`, JPQL, `@ElementCollection` для ролей |
| `payment` | Hibernate вручную | Criteria API; массовое обновление в обход контекста |
| `order`, `cart`, `delivery` | Spring JDBC | рукописный SQL, `RowMapper`, `FOR UPDATE SKIP LOCKED` |
| `audit` | голый JDBC | `Connection`, `PreparedStatement`, ручной разбор строк |

Внутри одного сервиса все подходы работают поверх одного `DataSource` и одного менеджера транзакций
(`JpaTransactionManager`): `JdbcTemplate` берёт соединение через `DataSourceUtils`
и попадает в ту же транзакцию, что и `EntityManager`.

### Шесть хранилищ и зачем каждое

PostgreSQL остаётся системой записи. Всё остальное — либо производные проекции, которые
можно потерять и построить заново, либо данные, которым реляционная модель не нужна.

| Хранилище | Модуль | Задача | Почему именно оно |
|---|---|---|---|
| PostgreSQL | всё ядро | заказы, деньги, пользователи | транзакции и целостность |
| Redis | catalog-service | кэш витрины | скорость чтения |
| Kafka | `order` → notification-service, `analytics` | события заказа | независимые потребители |
| MongoDB | `review` | отзывы с оценками блюд и метками | подвижная схема, вложенные документы |
| Cassandra | `tracking` | координаты курьера | поток вставок, чтение по одному ключу, TTL |
| Neo4j | `recommendation` | «с этим заказывают» | обход графа на два шага |
| ClickHouse | `analytics` | продажи по дням, воронка статусов | агрегаты по колонкам |
| Elasticsearch | catalog-service, `search` | поиск с морфологией и опечатками | разбор текста |

Способ доступа у каждого свой, и это продолжение того же осознанного разнобоя:

| Модуль | Подход | Что на нём видно |
|---|---|---|
| `review` | Spring Data MongoDB | репозитории; `$facet` в aggregation pipeline |
| `search` | Spring Data Elasticsearch | `ElasticsearchOperations`, Query DSL, `multi_match` с нечёткостью |
| `tracking` | голый драйвер DataStax | CQL руками, подготовленные запросы, `timeuuid` как ключ |
| `recommendation` | голый драйвер Neo4j | Cypher руками, `MERGE` ради идемпотентности |
| `analytics` | `JdbcTemplate` поверх своего пула | SQL руками, пакетная вставка, `ReplacingMergeTree` |

У Cassandra и Neo4j взяты драйверы, а не стартеры Spring Boot, и на это есть причины,
описанные в `CassandraConfig` и `Neo4jConfig`: стартер Cassandra открывает соединение
на старте контекста, а Spring Data Neo4j добавляет второй менеджер транзакций рядом
с `JpaTransactionManager`. ClickHouse не получает бина `DataSource` намеренно — второй
такой бин выключил бы автоконфигурацию основного пула; подробности в `ClickHouseJdbc`.

### Как данные попадают в производные хранилища

Три модуля из пяти работают с копиями, и каждый получает их по-своему. Разница
не случайна — она следует из того, что именно нужно потребителю.

| Куда | Как | Почему так |
|---|---|---|
| ClickHouse | потребитель Kafka, своя группа | событие уже содержит всё, что нужно витрине |
| Neo4j | циклическая сверка PostgreSQL пачками с курсором | учитывает состав заказа, отмены и поздние коммиты |
| Elasticsearch | полная переиндексация по расписанию | двойная запись оставила бы индекс расходящимся навсегда |

Отзывы в MongoDB и трек в Cassandra — единственные данные вне PostgreSQL, у которых нет
второго источника: их пишет сразу API, и восстановить их неоткуда.

Граф после конца выборки возвращает курсор к началу. Связи каждого заказа заменяются
атомарно; отменённый заказ удаляет свои прежние связи. Поэтому задержка изменения графа
зависит от длины полного прохода: примерно `(число пачек + 1) × интервал`, плюс время
обработки. Синхронизация ручного запуска, таймера и перестроения действует внутри одного
экземпляра приложения. Для большого объёма истории следующим шагом будет очередь изменений.

В отзыве можно оценить только блюда из доставленного заказа, каждое один раз. Название
сервер берёт из позиции заказа; присланное клиентом название не меняет сохранённый снимок.

Подробности каждого решения — в javadoc соответствующих репозиториев. Отправная точка —
`AuditLogRepository`: там же объяснено, почему голый JDBC обязан брать соединение
у `DataSourceUtils`, а не у `DataSource`.

### База данных

Схемой владеет Liquibase, и только он. Hibernate работает с `ddl-auto: validate` —
сверяет сущности с таблицами на старте и падает при расхождении, но ничего не меняет.

Миграции лежат в `service/src/main/resources/db/changelog/migrations/`, каждая ссылается
на файл с SQL. Прикладные таблицы живут в схеме `food_app`, журнал Liquibase — в
`liquibase_meta`.

Схему пяти дополнительных хранилищ Liquibase не трогает: у него нет для них диалектов,
да и незачем. Таблицу в Cassandra, таблицу в ClickHouse, индексы MongoDB и индексы
Elasticsearch создают на старте отдельные классы — `CourierTrackSchema`,
`OrderAnalyticsSchema`, `ReviewIndexes` и `SearchIndex`. Это осознанное упрощение,
допустимое ровно потому, что таблиц там по одной, а три из четырёх хранилищ содержат
производные данные: их не мигрируют, а строят заново.

### События и надёжность

Смена статуса заказа пишется в таблицу `order_event_outbox` в той же транзакции, что и сам
заказ. Отдельная задача разбирает очередь и отправляет события в Kafka. Так событие
не может уехать по откатившейся транзакции, а недоступный брокер не роняет оформление
заказа.

Продюсер идемпотентный, `acks=all`; необработанные сообщения уходят в DLT — у каждого
потребляющего сервиса свой.

### Наблюдаемость

Каждый запрос получает `X-Correlation-Id` в шлюзе (или использует присланный) и возвращает
его в ответе. Метка едет заголовком в сервис, оттуда метаданными gRPC в соседние сервисы
(`x-correlation-id`) и через outbox и Kafka в потребителей,
попадает в MDC и видна в каждой строке лога каждого сервиса — по ней запрос
прослеживается насквозь:

```bash
docker compose --profile full logs | grep <correlation-id>
```

Метрики отдаёт Actuator в формате Prometheus, дашборд Grafana поставляется в
`observability/grafana/provisioning/`.

## API

Источник истины по контракту — `openapi/food-delivery-api.yaml`. Из него генерируются
интерфейсы контроллеров для `service` и типизированный клиент в модуле `client`.

Спецификация описывает рестораны, меню и пять дополнительных модулей: отзывы, трекинг,
рекомендации, аналитику и поиск. Рестораны и меню реализуют сгенерированные интерфейсы;
для дополнительных модулей совместимость проверяется контрактными тестами клиента.
Живой контракт всего API отдаёт springdoc на `/swagger-ui.html`.

Готовая Postman-коллекция на весь API — в `postman/`, там же инструкция.

### Что добавили пять хранилищ

Маршруты появляются вместе с модулем: при выключенном хранилище контроллера нет и ответ
будет 404, а не 500 или пустой список. Так честнее — функциональности в такой сборке
действительно нет.

| Метод и путь | Кто | Что делает |
|---|---|---|
| `POST /api/v1/customers/{id}/orders/{orderId}/review` | клиент | отзыв о доставленном заказе |
| `GET /api/v1/restaurants/{id}/reviews` | все | отзывы постранично |
| `GET /api/v1/restaurants/{id}/reviews/summary` | все | среднее, гистограмма оценок, частые метки |
| `POST /api/v1/couriers/{id}/deliveries/{deliveryId}/positions` | курьер | отправить координату |
| `GET /api/v1/couriers/{id}/deliveries/{deliveryId}/track` | курьер | свой трек |
| `GET /api/v1/customers/{id}/orders/{orderId}/track` | клиент | где мой заказ |
| `GET /api/v1/search?q=&city=` | все | поиск по ресторанам и блюдам |
| `GET /api/v1/customers/{id}/recommendations` | клиент | что берут с похожим вкусом |
| `GET /api/v1/menu-items/{id}/ordered-together` | вошедшие | что заказывают вместе |
| `GET /api/v1/restaurants/{id}/analytics/sales` | владелец | продажи по дням |
| `GET /api/v1/restaurants/{id}/analytics/funnel` | владелец | воронка статусов |
| `GET /api/v1/admin/analytics/sales` | админ | продажи всей платформы |
| `POST /api/v1/admin/search/reindex` | админ | переиндексировать витрину сейчас |
| `POST /api/v1/admin/recommendations/project` | админ | догнать граф на одну пачку |
| `POST /api/v1/admin/recommendations/rebuild` | админ | построить граф заново |

Поиск и отзывы открыты без токена — по тому же признаку, что список ресторанов и меню:
это чтение публичного каталога.

### Аутентификация

JWT на RS256 от identity-service, роли `CUSTOMER`, `RESTAURANT_OWNER`, `COURIER`, `ADMIN`.
В токене — `sub` (идентификатор), `roles` и `email`; e-mail нужен журналам аудита, чтобы
не спрашивать сервис пользователей на каждую запись. Роль `ADMIN` через регистрацию
не выдаётся: первый администратор создаётся при старте identity-service из `APP_ADMIN_EMAIL`
и `APP_ADMIN_PASSWORD`, а если они не заданы — не создаётся вовсе.

Вход и регистрация выдают пару токенов. Access-токен (JWT) живёт 15 минут и проверяется
любым сервисом без обращения к identity-service — поэтому отозвать его нельзя. Refresh-токен —
случайная строка, живёт 30 дней и проверяется только по базе identity-service, поэтому
отзывается сразу:

| Запрос | Что делает |
|---|---|
| `POST /api/v1/auth/refresh` `{"refreshToken": "…"}` | новая пара; старый refresh-токен больше не действует |
| `POST /api/v1/auth/logout` `{"refreshToken": "…"}` | завершает эту сессию, другие устройства остаются |

Refresh-токен одноразовый. Если уже обменянный токен предъявят снова, значит, у него две копии,
и identity-service отзывает всю цепочку: войти заново придётся и владельцу, и тому, кто токен
украл. Блокировка пользователя администратором отзывает все его сессии. В базе хранится
только SHA-256 токена.

```bash
./mvnw clean verify                          # сборка и все тесты всех модулей
./mvnw -pl catalog-service -am verify        # один сервис и то, от чего он зависит
```

### CI и поставка

Монорепозиторий устроен так, чтобы его можно было разрезать на отдельные репозитории
без переделок: сервисы не зависят друг от друга по коду, собираются, проверяются
и поставляются по отдельности.

| Workflow | Когда | Что делает |
|---|---|---|
| `ci.yml` | PR и пуш в `dev`/`main` | собирает и тестирует **только затронутые** модули, каждый отдельным job; итоговая проверка `CI пройден` — для защиты ветки |
| `images.yml` | пуш в `dev`/`main` | собирает образы изменившихся сервисов и публикует в GHCR с тегами `<sha>` и `<ветка>` |
| `contracts.yml` | тег `contracts-vX.Y.Z` | публикует `event-contracts` и `grpc-contracts` в GitHub Packages |

Что считается «затронутым», описано в `ci.yml`: сам модуль, контракты, от которых он
зависит, и общая сборка (корневой pom, `mvnw`). Правка контракта запускает всех его
потребителей — ровно это и нужно проверить.

**Версии.** У контрактов своя версия (`contracts.version`, сейчас `1.0.0-SNAPSHOT`) и свои pom
без родителя платформы: потребителю не нужно тянуть за контрактом pom монолита. Совместимое
изменение — минорная версия, несовместимое — мажорная и новый пакет `.proto` (`catalog.v2`).
Сервисы поставляются образами, и их версия — это sha коммита в теге образа.

**Готовые образы.** Поднять стек из того, что собрал CI, без локальной сборки:

```bash
docker login ghcr.io          # пакеты репозитория приватные
IMAGE_TAG=dev docker compose --profile full pull
IMAGE_TAG=dev docker compose --profile full up -d --no-build
```
