# 1. Доставка в реальном времени

Как сервер сообщает клиенту, что что-то изменилось. В проекте используются все основные способы,
и каждый стоит там, где он лучше остальных.

## Пять способов

```
polling        клиент ──GET──▶ сервер  «есть новое?» «нет» … «нет» … «да»     (раз в N секунд)
long polling   клиент ──GET──▶ сервер  ……… держит запрос ……… ◀── «да» / 304 по таймауту
SSE            клиент ──GET──▶ сервер  ◀── событие ◀── событие ◀── пульс ◀── событие   (один поток)
WebSocket      клиент ◀══════▶ сервер  кадры в обе стороны по одному соединению
webhook        сервер ──POST──▶ сервер партнёра   (клиент — не браузер, а чужой бэкенд)
```

| | Задержка | Нагрузка на сервер | Через прокси | В обе стороны | Где в проекте |
|---|---|---|---|---|---|
| Polling | до N секунд | запрос каждые N с на каждого клиента, почти все пустые | без проблем | нет | запасной режим веб-интерфейса, пока поток недоступен |
| Long polling | почти ноль | один «висящий» запрос на клиента, повтор после каждого ответа | без проблем: обычные HTTP-ответы | нет | лента уведомлений, свободные доставки курьера |
| SSE | почти ноль | одно соединение на клиента | нужно отключить буферизацию и поднять таймауты | нет (сервер → клиент) | статус заказа клиента, доска заказов ресторана |
| WebSocket | почти ноль | одно соединение на клиента, своё состояние | нужен Upgrade, отдельные таймауты | да | трек курьера, чат заказа |
| Webhook | почти ноль | запрос на событие | — | нет | фаза 2: события заказов партнёрам |

**Как выбирать.** Нужен ответ в обе стороны (чат, «печатает…») — WebSocket. Только сервер → клиент
и важно продолжить с места обрыва — SSE. Клиент простой, за чужими прокси, или каждый ответ должен
быть законченным кэшируемым HTTP-обменом — long polling. Получатель — чужой сервер — вебхук.
Обычный опрос хорош как страховка: он работает всегда.

## SSE: статус заказа и доска ресторана

`order-service/src/main/java/com/dima/fooddelivery/live/`

```
GET /api/v1/customers/{c}/orders/{o}/stream        Last-Event-ID: 41
                                                    ─────────────────────────────
                                                    id: 42
                                                    event: order-event
                                                    data: {"id":42,"eventType":"ORDER_ACCEPTED",…}

                                                    event: status
                                                    data: {"orderId":7,"status":"ACCEPTED"}

                                                    : keepalive          ← пульс раз в 15 с
                                                    …
                                                    event: end           ← заказ доставлен, поток закрыт
```

- **Продолжение с места обрыва.** У каждого события истории есть `id`. Клиент после обрыва
  переподключается с `Last-Event-ID` и получает только то, чего не видел (`OrderStreams`).
- **Токен — в заголовке.** Браузерный `EventSource` не умеет `Authorization`, а токен в адресе
  попал бы в логи nginx и шлюза. Поэтому веб-интерфейс читает поток через `fetch` и сам разбирает
  формат `text/event-stream` (`web/js/live.js`, функция `sseStream`).
- **Поток не держит поток Tomcat.** Контроллер возвращает `SseEmitter` и освобождает поток;
  соединение держит контейнер. Повторный проход запроса (async dispatch) пропускается в Spring
  Security без проверки токена — права проверены на первом проходе (`SecurityConfig`).
- **Потолок соединений.** `LIVE_MAX_STREAMS` (500 на экземпляр) — дальше честный `503` с
  `Retry-After`, а не медленная смерть (`StreamLimiter`, метрика `live.streams.open`).
- **Доска ресторана — fan-out.** Один сигнал «заказ N теперь ACCEPTED» уходит во все открытые
  вкладки всех сотрудников ресторана (`RestaurantBoardStreams`). Истории тут нет: после
  переподключения доска просто перечитывает список — это дешевле, чем восстанавливать пропуски.

## Long polling: курьеры и уведомления

**Свободные доставки** (`order-service/.../live/DeliveryOfferWaiters.java`):

```
GET /deliveries/available/poll              If-None-Match: "a1b2-3"
  ├─ версия списка другая          → 200 + список + ETag: "c4d5-4"     (сразу)
  ├─ та же → ждём сигнала ……………… → 200 + новый список                (как только изменился)
  └─ 25 секунд ничего               → 304 Not Modified                 (клиент тут же повторяет)
```

Версия списка — стандартный `ETag`: контрольная сумма идентификаторов свободных доставок.
Запрос паркуется в `DeferredResult` — поток Tomcat свободен.

**Лента уведомлений** (`notification-service/.../live/NotificationPollWaiters.java`): курсор —
идентификатор последнего полученного уведомления, `?after=<id>`. Ответ `{items, nextAfter}`;
пустой список — таймаут. Курсор делает ответы идемпотентными: повтор того же запроса вернёт то же.

## Fan-out между экземплярами: три механизма

Клиент подключён к экземпляру A, а изменение записал экземпляр B. Как A узнает? В проекте три
разных ответа — у каждого свои свойства.

### PostgreSQL LISTEN/NOTIFY — order-service

```
транзакция: UPDATE customer_order … ; INSERT customer_order_event … ; SELECT pg_notify('live_updates','order:7:3:ACCEPTED')
                                                      │ доставляется только после COMMIT
          ┌───────────────────────────────────────────┴──────────────────┐
   экземпляр A: LISTEN live_updates                            экземпляр B: LISTEN live_updates
```

- **Транзакционность.** `NOTIFY` внутри транзакции уходит только после коммита и пропадает при
  откате. Не бывает сигнала о том, чего нет в базе, и не нужен отдельный шаг «после коммита»,
  который может не выполниться (`LiveSignals`).
- **Своё соединение.** `LISTEN` живёт, пока живо соединение, поэтому у слушателя оно своё, мимо
  пула Hikari, с переподключением и нарастающей паузой (`PgNotificationListener`).
- **Цена:** сигнал не хранится. Кто не слушал в момент коммита, его не получит. Поэтому
  сигнал — только «звонок в дверь» (см. ниже), а после переподключения каждый канал догоняет
  подписчиков из базы.

### RabbitMQ fanout — notification-service

```
после коммита ──▶ notifications.live (fanout) ──┬──▶ notifications.live.<A> (анонимная, эксклюзивная) ──▶ A
                                                 └──▶ notifications.live.<B> ──▶ B
```

Fanout копирует сообщение в каждую привязанную очередь, а очередь у каждого экземпляра своя и
исчезает вместе с ним (`NotificationLiveTopology`). Это publish/subscribe — в противоположность
рабочим очередям того же сервиса (`notifications.email` и др.), где сообщение получает один
обработчик из многих (конкурирующие потребители). Оба шаблона на одном брокере; различает их тип
обмена и то, общая очередь или у каждого своя.

### STOMP-ретранслятор в RabbitMQ — tracking-service

Трек и чат идут в `amq.topic` через STOMP-плагин RabbitMQ: брокер сам доставляет кадр каждому
подписанному WebSocket-соединению на любом экземпляре. Встроенный брокер Spring держал бы
подписки в памяти одного процесса.

| | PostgreSQL NOTIFY | RabbitMQ fanout | STOMP relay |
|---|---|---|---|
| Новая инфраструктура | нет, база уже есть | брокер уже есть | брокер уже есть |
| Привязка к транзакции | да, атомарно с данными | нет, после коммита | нет |
| Хранение сигнала | нет | нет (у нас — непостоянные сообщения) | нет |
| Кому доставляет | экземплярам этого сервиса | экземплярам этого сервиса | напрямую браузерам |

## «Сигнал + чтение» вместо «посылки»

Во всех трёх случаях сигнал говорит **где** изменилось, но не несёт данных. Данные получатель
читает из базы. Отсюда:

- потерянный сигнал не теряет событий — их заберёт следующий сигнал или переподключение;
- повторный сигнал безвреден — дочитывать нечего;
- порядок сигналов не важен — порядок задаёт база.

Тот же приём в notification-service уже был: задача в RabbitMQ — только «займись уведомлением N»,
а страховочный опрос подбирает потерянные задачи.

**Известное ограничение.** Поток клиента дочитывает события с `id > lastEventId`, а идентификатор
выдаётся при вставке, не при коммите. Если две транзакции вставят события 10 и 11, а закоммитится
сначала 11, клиент увидит 11 и пропустит 10. Смены статуса одного заказа сериализует блокировка
строки заказа, поэтому для них порядок честный; полное решение — свой счётчик событий на заказ.

## Thundering herd

Сигнал «список доставок изменился» будит сразу всех ждущих курьеров. Если каждый пойдёт в базу
за списком, один сигнал превратится в сотню одинаковых запросов. Поэтому `DeliveryOfferWaiters`
читает список **один раз** и раздаёт его всем ждущим, а сигналы, пришедшие во время чтения,
схлопываются в одно повторное чтение (флаг `refreshScheduled`). Тот же приём на клиенте: пачка
кадров SSE (история при подключении) вызывает одно перечитывание заказа, а не десять.

## Что ломает долгие соединения

| Где | Проблема | Что сделано |
|---|---|---|
| Шлюз | общий `response-timeout: 15s` оборвал бы поток на 15-й секунде | отдельные маршруты `*-live` с `response-timeout: -1` (`api-gateway` `application.yml`, тест `LiveRoutesIT`) |
| nginx | буферизует ответ и отдаёт кадры пачкой; рвёт молчащее соединение через 60 с | заголовок `X-Accel-Buffering: no` в ответе SSE; пульс раз в 15 с; long polling ждёт не дольше 30 с |
| Плавное завершение | ждёт все открытые запросы до таймаута — поток SSE сам не кончится | на остановке потоки закрываются, а ждущие получают пустой ответ раньше, чем остановится веб-сервер (`SmartLifecycle`) |
| Токен | живёт 15 минут, а соединение — дольше | поток доживает до конца; при переподключении клиент получает 401 и обменивает refresh-токен (`web/js/live.js`) |

## Чат заказа: WebSocket в обе стороны

`tracking-service/src/main/java/com/dima/fooddelivery/chat/`

```
отправка:  POST /api/v1/orders/{o}/chat/messages {text, clientMessageId} ─▶ Cassandra ─▶ /topic/order.{o}.chat
приём:     WebSocket /ws/tracking ─ SUBSCRIBE /topic/order.{o}.chat ◀── MESSAGE | TYPING | READ
эфемерное: SEND /app/order.{o}.chat.typing   SEND /app/order.{o}.chat.read {upTo}
```

- **Сообщение — по HTTP, доставка — по WebSocket.** У HTTP есть всё, чего нет у кадра STOMP:
  код ответа (400, 404, 409, 429), повтор без дубликата, лимиты шлюза, журнал запросов.
  Эфемерные сигналы («печатает», «прочитано») ответа не требуют — они идут кадрами.
- **Участники — по заказу, а не по роли.** Роль COURIER есть у всех курьеров, а писать может
  только тот, кто везёт этот заказ (`ChatParticipants`, вопрос к order-service по gRPC).
- **Идемпотентность и лимит частоты** — в [главе 2](02-idempotency-and-rate-limiting.md).

клиента сразу после нажатия у ресторатора, рядом с номером заказа горит «● обновляется вживую».
