# 3. Вебхуки и ключи API

Вебхук — это «позвони мне, когда что-то случится», только звонит сервер серверу: при событии
платформа сама делает HTTP-запрос на адрес, который ей заранее дали. В проекте вебхуки идут в обе
стороны:

```
исходящие:  событие заказа ─▶ notification-service ─POST, подпись─▶ CRM / касса ресторана
входящие:   Stripe   ─POST, Stripe-Signature─────────▶ payment-service
            Telegram ─POST, секретный заголовок──────▶ notification-service
```

Ключи API — способ для чужой системы (кассы ресторана) самой ходить в платформу без пароля
человека.

## Исходящие вебхуки

`notification-service/src/main/java/com/dima/fooddelivery/notification/webhook/`

```
Kafka order-events ──(своя группа notification-webhooks)──▶ WebhookFanout
   │  одна транзакция: доставка на каждую подходящую подписку (UNIQUE подписка+событие)
   ▼ после коммита
RabbitMQ webhooks.dispatch ─▶ webhooks.deliveries ─▶ WebhookDispatcher
                                   ▲                     │ аренда → POST с подписью
                                   │ TTL истёк           ├─ 2xx  → SUCCEEDED
                                   └─ webhooks.retry.*  ◀┤─ иначе → следующая ступень лестницы
                                                         ├─ 410  → подписка выключена сразу
                                                         └─ ступени кончились → FAILED (+ автовыключение после 20 подряд)
```

### Доставка «хотя бы один раз» и идемпотентность получателя

Платформа не может гарантировать «ровно один раз»: ответ получателя мог потеряться после того, как
он всё сделал. Поэтому:

- **платформа** повторяет, пока не получит 2xx, и шлёт все попытки с одним заголовком `webhook-id`
  (идентификатор события);
- **получатель** запоминает обработанные `webhook-id` и повтор просто подтверждает — та же схема
  inbox, что у потребителей Kafka в проекте.

Тело доставки собирается один раз и хранится в базе: все попытки и ручные повторы шлют байт в байт
одно и то же, иначе подпись первой попытки не совпала бы с телом второй.

### Подпись (Standard Webhooks)

```
webhook-id:        6f1c…                     ← один во всех попытках
webhook-timestamp: 1730041200                ← время этой попытки
webhook-signature: v1,K5oZ…= v1,Qm2x…=       ← HMAC-SHA256(секрет, id.timestamp.тело), по подписи на секрет
```

| Что защищает | От чего |
|---|---|
| HMAC с общим секретом | подделки: без секрета подпись не построить |
| timestamp внутри подписи | повтора перехваченного запроса через час (получатель отвергает старше 5 минут) |
| id внутри подписи | подмены id ради обхода дедупликации |
| несколько подписей | обрыва интеграции при ротации секрета: сутки запрос подписан и старым, и новым |

Секрет хранится **зашифрованным** (AES-256-GCM, ключ `WEBHOOK_SECRET_KEY`), а не хешем: пароль
достаточно сверить, а секретом вебхука нужно подписывать — значит, нужен он сам (`SecretCipher`).

### Повторы: лестница очередей, а не sleep

Пауза между попытками растёт: 10 с, 1 мин, 5 мин, 30 мин, 2 ч. Каждая ступень — своя очередь
RabbitMQ со своим TTL; истёкшее сообщение брокер сам возвращает в рабочую очередь
(dead-letter exchange). Почему не одна очередь с TTL на сообщение: брокер проверяет срок только у
головы очереди, и короткий срок застрял бы за длинным (`WebhookTopology`).

**Jitter.** Когда упавший получатель поднимается, на него разом идут все накопленные повторы.
Случайная добавка к паузе (jitter) размазывает их во времени — так делают AWS SDK и большинство
клиентов. С TTL на очередь jitter не сделать (пауза общая для ступени); варианты — плагин
отложенных сообщений RabbitMQ или расписание в базе (`next_attempt_at` + опрос). В проекте нагрузку
ограничивает параллельность обработчика (`WEBHOOK_CONCURRENCY`), а это компромисс записан явно.

**Очередь «мёртвых» писем** — сама таблица доставок: FAILED с кодом ответа и текстом ошибки, а у
владельца кнопка «Доставить заново».

### Аренда (lease)

Одна доставка может оказаться в очереди дважды (страховочный опрос + исходное сообщение).
Обработчик сначала занимает её: `UPDATE … SET locked_until = now()+30s WHERE status='PENDING' AND
(locked_until IS NULL OR locked_until < now())`. Отправляет только тот, кому вернулась одна
строка; аренда упавшего обработчика истекает сама. В отличие от `SELECT … FOR UPDATE`, транзакция
не держится открытой, пока идёт HTTP-запрос к чужому серверу.

### SSRF

Адрес задаёт партнёр, а запрос делает наш сервер изнутри нашей сети. Без защиты вебхук на
`http://169.254.169.254/` (метаданные облака с ключами) или `http://postgres:5432` превратил бы
платформу в прокси во внутреннюю сеть. `WebhookUrlGuard`:

- только `https`;
- все адреса, в которые разрешается имя, — публичные (не loopback, 10/8, 172.16/12, 192.168/16,
  169.254/16, 100.64/10, fc00::/7);
- проверка повторяется перед каждой попыткой (DNS rebinding: имя было публичным при подписке,
  а потом стало указывать внутрь);
- перенаправления не выполняются.

Остаточное окно — между проверкой и соединением имя может разрешиться иначе. Полное решение —
соединяться ровно с проверенным IP или выпускать вебхуки через исходящий прокси (smokescreen).

### Автовыключение

Подписка на мёртвый адрес вечно занимала бы обработчики и очередь повторов. После 20 проваленных
доставок подряд (или сразу по `410 Gone`) она выключается с понятной причиной; владелец включает её
кнопкой. Это тот же принцип, что у circuit breaker: перестать бить в то, что не отвечает.

## Входящие вебхуки

### Stripe — `payment-service/.../payment/webhook/`

Платёж проводится синхронно, исход списания сервис знает из ответа Stripe. Вебхук нужен для того,
что происходит **вне нашего вызова**: возврат из кабинета Stripe, оспаривание платежа, и сверка
(reconciliation) — если наш вызов оборвался по таймауту, а Stripe платёж провёл.

- **Подпись** `Stripe-Signature: t=…,v1=…` — HMAC от `t + "." + сырое тело`. Тело принимается
  строкой: разобранный и собранный заново JSON уже не совпадёт с подписью.
- **Окно 5 минут** и **сравнение за постоянное время** — как у исходящих.
- **Inbox по `evt_…`** в той же транзакции, что изменение платежа: Stripe повторяет до трёх суток.
- **Сверка не перезаписывает финальное.** PENDING доводится до исхода; если у нас FAILED, а у
  Stripe SUCCEEDED — это лог и метрика `payment.reconciliation.mismatch` для человека. Тихо
  «исправлять» деньги нельзя.

Коды ответа по правилам провайдера: 2xx — «больше не присылай»; неверная подпись — 400; сбой
обработки — 500 (повтор поможет).

### Telegram — опрос или вебхук

| | Long polling (по умолчанию) | Вебхук (`TELEGRAM_MODE=webhook`) |
|---|---|---|
| Кто инициирует | сервис: `getUpdates`, запрос висит до 25 с | Telegram: POST на наш адрес |
| Что нужно | только исходящий интернет | публичный https-адрес |
| Подлинность | ответ на наш же запрос | секрет в заголовке `X-Telegram-Bot-Api-Secret-Token` |
| Несколько экземпляров | опрашивает один, у второго 409 | любой за балансировщиком |
| Задержка | почти ноль | почти ноль |

Позиция (`offset`) общая: при вебхуке обновление с номером меньше сохранённого уже обработано и
пропускается. Переход обратно на опрос снимает вебхук (`deleteWebhook`) — иначе `getUpdates`
отвечает 409.

## Ключи API партнёров

`identity-service/.../apikey/`

```
владелец в кабинете ─POST /auth/api-keys─▶ fdp_k3x9a2bq_Vt7…(32)   ← показан один раз
касса ─POST /auth/api-keys/token, X-Api-Key─▶ access-токен на 15 минут ─▶ любые API от имени владельца
```

- **В базе — только SHA-256 секрета.** bcrypt нужен паролям: их мало, их перебирают по словарю.
  32 случайных символа — это ~190 бит, перебор невозможен при любой скорости хеша.
- **Префикс открыт** — по нему ключ находится в базе и узнаётся в списке и логах (как `sk_live_…`
  у Stripe или `ghp_…` у GitHub — такие префиксы ещё и ловят сканеры утечек в репозиториях).
- **Обмен на токен, а не ключ в каждом запросе** — схема client credentials: сервисы по-прежнему
  проверяют JWT без похода в базу; отзыв ключа срабатывает на следующем обмене (≤ 15 минут).
- **Ключом нельзя управлять ключами** — иначе утёкший ключ выпустил бы себе замену до отзыва.
- **Одна ошибка на все отказы** — «нет такого префикса», «не тот секрет» и «отозван» неразличимы.
- **Следующий шаг** — scopes (ключ только на чтение заказов одного ресторана): claims токена
  и проверка их в сервисах.

## Безопасная выкатка

Новый образ notification-service требует `WEBHOOK_SECRET_KEY`, а compose с ним — отдельный PR
платформы. Если бы сервис без ключа не стартовал, порядок слияния PR ломал бы стенд. Поэтому без
ключа выключены только вебхуки (API — 503), а сервис работает: **код можно выкатить раньше
конфигурации**. Неверный ключ — другое дело, это ошибка, и старт падает. Тот же принцип
«expand → migrate → contract» используется для схемы базы: сначала совместимое расширение, потом
переход, потом уборка старого.

```bash
curl -X POST -H "X-Api-Key: fdp_…" http://localhost:8080/api/v1/auth/api-keys/token
```
