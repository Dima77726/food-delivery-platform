# 5. Бизнес-функции: гео-индекс, отложенные задачи, блокировки, промокоды, цена

Автоназначение курьера, заказы ко времени, промокоды, динамическая цена доставки, чаевые и частичные
возвраты. Сами функции несложные; интересно, на каких механизмах они стоят. Почти весь код —
в `order-service/src/main/java/com/dima/fooddelivery/{dispatch,pricing,promo,refund}`.

## Из чего складывается сумма заказа

`pricing/CheckoutPricing.java`, `pricing/OrderTermsRepository.java`, таблица `order_terms`

```
еда (корзина)  − скидка по промокоду  + доставка (база × коэффициент спроса)  + чаевые  = к оплате
   1000 ₽             −100 ₽                    149 ₽ × 1,5 = 224 ₽              +100 ₽     1224 ₽
```

- **Условия — отдельная таблица, а не новые колонки заказа.** У старых заказов условий нет
  (`terms: null` в ответе), и ни одна строка `customer_order` не переписывается миграцией.
- **Цена фиксируется при оформлении.** Коэффициент спроса меняется каждые 30 секунд; клиент платит
  тот, что видел, — он записан в `order_terms.surge_multiplier`. Так же устроены «price lock» в такси.
- **Ресторан получает за еду.** Скидку оплачивает платформа: в ежедневных расчётах
  (`settlement/SettlementJobConfig.java`) выручка ресторана — `items_total`, а не итог заказа.

## Курьеры на карте: Redis GEO

`dispatch/CourierPresence.java`

```
PUT /couriers/42/presence {online, lat, lon}   (раз в 30 с, пока курьер на линии)
   GEOADD couriers:geo lon lat "42"            точка в гео-индексе
   SET couriers:alive:42 1 EX 90               пульс
поиск: GEOSEARCH couriers:geo FROMLONLAT lon lat BYRADIUS 5 km ASC COUNT n WITHDIST
       → отбрасываем тех, у кого пульс истёк
```

- **Как Redis ищет по радиусу.** GEO — это обычный sorted set: координаты превращаются в 52-битный
  **geohash** (биты долготы и широты чередуются) и лежат в score. Близкие точки чаще всего имеют
  общий префикс, поэтому поиск по радиусу — несколько диапазонов score по соседним ячейкам плюс
  точная проверка расстояния. Это та же идея, что у индексов S2/H3 у Uber и у GiST в PostGIS.
- **Почему не PostGIS.** Позиции меняются каждые несколько секунд у тысяч курьеров; писать их в
  транзакционную базу с индексом дорого, а терять — не страшно (через 30 с придёт новая). Redis держит
  их в памяти. История треков при этом живёт в Cassandra (tracking-service), это другая задача.
- **TTL на элемент zset поставить нельзя**, поэтому «жив ли курьер» — отдельный ключ с TTL 90 с, а
  раз в минуту задача вычищает из индекса тех, чей пульс пропал. Приложение упало, сеть пропала —
  курьер выпадает из поиска сам, без явного «ушёл с линии».
- **Не использовать `KEYS`.** Подсчёт курьеров на линии перебирает члены zset, а не `KEYS couriers:alive:*`
  — `KEYS` блокирует однопоточный Redis на всё время обхода ключей.

## Автоназначение: предложение, а не приказ

`dispatch/DispatchService.java`, таблица `delivery_offer`

```
такт раз в 5 с (один экземпляр — ShedLock)
  1. OFFERED с истёкшим сроком → EXPIRED; по доставкам, которые уже взяли вручную → CANCELED
  2. доставка без курьера и без действующего предложения:
       GEOSEARCH от адреса, 5 км  − отказавшиеся/пропустившие её  − занятые  − с открытым предложением
       → INSERT delivery_offer (OFFERED, истекает через 30 с)
курьер «Беру»:  UPDATE … SET ACCEPTED WHERE id=? AND courier_id=? AND status='OFFERED' AND expires_at > now()
                → обычное назначение (assignCourier с проверкой статуса)
курьер «Не могу»: DECLINED → на следующем такте следующему по расстоянию
```

- **Почему предложение.** Ближайший курьер может стоять в пробке, разряжаться или уже везти заказ
  мимо приложения. Принудительное назначение «повесило» бы заказ на того, кто его не повезёт.
  Таймаут возвращает заказ в оборот без участия человека.
- **Одно предложение на доставку держит база**: частичный уникальный индекс
  `ON delivery_offer (delivery_id) WHERE status = 'OFFERED'`. Даже если такт выполнится на двух
  экземплярах одновременно, второй INSERT упадёт с `DuplicateKeyException`, и доставка не уйдёт двоим.
- **Принять можно только своё и только вовремя** — всё в одном условном UPDATE (compare-and-set).
  Опоздавший на секунду курьер получит 409, а не украдёт заказ у следующего.
- **Жадный алгоритм.** Каждой доставке — ближайший свободный. Глобально оптимальное распределение
  (венгерский алгоритм, батчинг заказов раз в N секунд) экономит километры при большом потоке;
  здесь важнее простота и предсказуемость.
- **Ручной путь остаётся**: список свободных доставок работает как раньше.
- **Компромисс.** Точка отсчёта — адрес клиента, потому что координат ресторанов в каталоге нет.
  Правильнее искать от ресторана; когда координаты появятся, меняется одна строка запроса.

## Отложенные задачи: «за час до срока напомнить ресторану»

`pricing/ScheduledOrders.java`

```
order_terms.scheduled_for = 19:30, prep_reminded_at = NULL
раз в минуту: SELECT … WHERE scheduled_for <= now() + 60 мин AND prep_reminded_at IS NULL AND статус PAID/ACCEPTED
             → UPDATE … SET prep_reminded_at = now() WHERE prep_reminded_at IS NULL  (только одна запись выигрывает)
             → событие «Пора готовить: заказ ко времени 19:30»
```

Как ещё делают отложенные задачи и почему здесь не так:

| Способ | Плюс | Почему не здесь |
|---|---|---|
| Опрос базы по сроку (здесь) | состояние задачи в той же транзакции, что и заказ; переживает всё | точность — период опроса (минута) |
| RabbitMQ: TTL + dead letter | уже есть в проекте (лестница повторов вебхуков) | TTL проверяется только у головы очереди: «через 3 дня» загородит «через час». Годится, когда задержка у всех одинаковая |
| Плагин delayed-message | любые задержки | хранит сообщения на одном узле, не реплицируется |
| Redis ZSET (score = время) | миллионы задач, точность до секунды | второе хранилище состояния, которое надо согласовывать с заказом |
| Quartz, Temporal | расписания, повторы, долгие процессы | отдельная инфраструктура ради одной задачи |

Срок «не раньше» тоже проверяется: начать готовить заказ ко времени раньше окна сервис не даст
(`OrderService.startCookingOrder`), иначе еда остынет к 19:30.

## Распределённая блокировка: ShedLock

`pricing/SchedulingLockConfig.java`, таблица `shedlock`

У `@Scheduled` нет понятия кластера: при трёх экземплярах сервиса задача выполнится трижды.
ShedLock перед запуском делает в базе условную запись:

```
UPDATE shedlock SET lock_until = now() + lockAtMostFor, locked_by = 'host'
WHERE name = 'courier-dispatch' AND lock_until <= now()
-- 1 строка — выполняем; 0 строк — другой экземпляр уже работает, пропускаем такт
```

- **`lockAtMostFor`** — страховка от упавшего держателя: экземпляр умер посреди такта — через
  30 секунд блокировку возьмёт другой. Значение должно быть больше самого долгого такта, иначе две
  копии пересекутся.
- **`usingDbTime()`** — время берётся у базы, а не у экземпляров: расхождение часов между машинами
  иначе ломает сравнение `lock_until <= now()`.
- **Блокировка — не гарантия единственности.** Пауза GC длиннее `lockAtMostFor` — и задача
  выполнится дважды. Поэтому каждая задача ещё и идемпотентна сама: напоминание пишется условным
  UPDATE, предложение — под уникальным индексом. Это общее правило: распределённая блокировка
  повышает эффективность, а корректность держат условия в базе (Мартин Клеппман о Redlock — про это).
- Где применено: автоназначение, пересчёт коэффициента спроса, напоминания о заказах ко времени.

## Промокоды: последнее использование продаётся один раз

`promo/PromoService.java`, `promo/PromoRepository.java`

```
UPDATE promo_code SET used_count = used_count + 1
WHERE code = ? AND active AND used_count < max_uses AND now() BETWEEN valid_from AND valid_until
-- 1 строка — использование наше; 0 — кончились или код недействителен
INSERT INTO promo_redemption (code, customer_id, order_id)   -- PK (code, customer_id): один раз на клиента
```

- **Гонка «прочитал — проверил — записал».** Наивно: `SELECT used_count`, сравнить с лимитом, `UPDATE`.
  Восемь одновременных оформлений прочитают одно и то же «осталось 1» и все пройдут. Условие внутри
  UPDATE выполняется атомарно под блокировкой строки — проходит ровно один (тест
  `CheckoutPricingIT.shouldSellLastPromoUseExactlyOnceUnderRace` запускает 8 потоков).
- Альтернативы: `SELECT … FOR UPDATE` (то же, но блокировка дольше), `DECR` в Redis (быстрее, но счётчик
  отдельно от заказа — при откате заказа его надо вернуть руками).
- Всё — в транзакции оформления: заказ не создался — использование откатилось вместе с ним.

## Фильтр Блума перед таблицей промокодов

`promo/PromoBloomFilter.java`

```
m = 65 536 бит (8 КБ в Redis), k = 4 хеша, n ≈ 1000 кодов → ложных «возможно, есть» ≈ 0,0002 %
добавить: SETBIT promo:bloom h_i(code) 1, i = 1..4
проверить: GETBIT ×4 конвейером → хоть один 0 — «точно нет», в базу не идём
h_i = h1 + i·h2 (CRC32 и FNV-1a — «двойное хеширование» Кирша–Митценмахера)
```

- **Зачем.** Промокоды перебирают ботами и вводят с опечатками. Несуществующий код отсекается одним
  походом в Redis; в базу идут только «возможно, есть». Классика: так же Cassandra и RocksDB не читают
  SSTable, в которой ключа точно нет.
- **Ложных «нет» быть не должно** — это единственная гарантия фильтра. Отсюда решения:
  - фильтр общий, в Redis: в памяти каждого экземпляра новый код, созданный на соседнем, был бы «нет»
    до следующей перестройки;
  - Redis платформы работает с `allkeys-lru` и может вытеснить ключ. Нет ключа (или Redis недоступен) —
    ответ «возможно, есть», и решает база. Добавление кода в отсутствующий фильтр не создаёт ключ
    с одним кодом, а перестраивает фильтр целиком из базы;
  - удалить код из фильтра нельзя (бит общий с другими кодами), поэтому раз в час — полная перестройка
    во временный ключ и атомарный `RENAME`.

## Динамическая цена доставки

`pricing/SurgePricing.java`

```
раз в 30 с (ShedLock):
  ratio = ждут курьера / курьеров на линии
  raw   = clamp(1 + 0,5·(ratio − 1), 1, 2)
  next  = round(0,5·raw + 0,5·prev, 0,1)        экспоненциальное сглаживание
  SET pricing:surge "next:waiting:online"
оформление: доставка = 149 ₽ × next, коэффициент записывается в заказ
```

- **Сглаживание (EMA)** гасит скачки: один всплеск заказов не должен удваивать цену на 30 секунд, а
  потом сбрасывать. Цена меняется плавно и не чаще такта.
- **Считает один экземпляр, читают все.** Без ShedLock три экземпляра с разным видом на данные
  записывали бы разные коэффициенты по очереди.
- **Ключа нет — коэффициент 1,0.** Redis пуст после перезапуска — доставка по базовой цене, а не ошибка.
- Цена — рычаг баланса: выше цена → часть клиентов подождёт, а в настоящих сервисах курьерам ещё и
  доплачивают за выход на линию в часы пик.

## Чаевые

Чаевые — часть суммы заказа, их видно курьеру в предложении и в заработке
(`GET /couriers/{id}/earnings`: доставлено и сумма чаевых). Верхняя граница (`app.pricing.max-tip`)
защищает от опечатки «10000» вместо «100».

## Частичные возвраты

`refund/RefundService.java`, payment-service: `PaymentService.partialRefund`

```
клиент: «не привезли напиток» → заявка (позиции, количество ≤ остатка, в течение 2 дней после доставки)
  ≤ 500 ₽ и не больше двух одобренных за 30 дней → одобряется сразу
  иначе → поддержка (Промо и возвраты в интерфейсе администратора)
одобрение: PENDING→APPROVED (условный UPDATE) + команда REFUND_REQUESTED {amount, key=partial-refund:<uuid>}
           в outbox, в одной транзакции
payment-service: UPDATE payment SET refunded_amount = refunded_amount + ? WHERE refunded_amount + ? <= amount
                 → провайдер с тем же ключом идемпотентности → PAYMENT_REFUNDED на сумму
```

- **Сумма считается на сервере** из цен позиций заказа; клиент присылает только какие позиции.
- **Нельзя вернуть больше списанного** — проверка внутри UPDATE и CHECK в схеме.
- **Повторная доставка команды** (Kafka — «хотя бы один раз») не вернёт деньги дважды: ключ
  `partial-refund:<id заявки>` уходит провайдеру, а сама заявка одобряется условным UPDATE один раз.
- **Автоодобрение — компромисс** между скоростью для честных клиентов и злоупотреблениями: порог и
  лимит частоты — простейший «антифрод»; настоящие системы считают вероятность мошенничества моделью.

## Вопросы для самопроверки

1. Почему предложение курьеру защищено уникальным индексом, если такт и так под ShedLock?
2. Что случится с промокодами, если Redis вытеснит фильтр, а код фильтра проверяет только биты?
3. Почему отложенные «через 3 дня» и «через час» плохо уживаются в одной очереди RabbitMQ с TTL?
4. Какой будет коэффициент спроса через минуту, если 20 доставок ждут, а на линии 5 курьеров?
5. Как сделать так, чтобы курьер не мог принять предложение после истечения 30 секунд, даже если
   такт, переводящий его в EXPIRED, ещё не прошёл?
