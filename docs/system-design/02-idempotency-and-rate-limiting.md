# 2. Идемпотентность и ограничение частоты

Сеть ненадёжна: ответ может потеряться *после* того, как сервер всё сделал. Клиент, не получивший
ответа, повторит запрос — и сервер обязан понять, что это повтор. А клиент с ошибкой (или залипшая
кнопка) может слать запросы без остановки — и сервер обязан это ограничить.

## Ключ идемпотентности

Клиент придумывает уникальный ключ **один раз на действие** и повторяет его в каждой попытке.
Сервер запоминает «ключ → результат» и на повтор возвращает тот же результат, ничего не делая заново.

| Где | Ключ | Как сервер узнаёт повтор |
|---|---|---|
| Оплата заказа (order-service) | `idempotencyKey` в теле `POST …/payments` | ключ пишется в строку заказа одним `UPDATE` вместе с переходом в `PAYMENT_PENDING` |
| Обработка событий Kafka (все потребители) | `eventId` события | уникальный индекс в таблице inbox / уведомлений: повтор — нарушение констрейнта |
| Сообщение чата (tracking-service) | `clientMessageId` | лёгкая транзакция Cassandra `INSERT … IF NOT EXISTS` |

**Почему не «проверить, а потом вставить».** Два одинаковых запроса могут прийти одновременно на
два экземпляра; оба проверят «ключа нет», оба вставят. Решать должна атомарная операция хранилища:
уникальный индекс в PostgreSQL, лёгкая транзакция в Cassandra.

### Чат: лёгкая транзакция Cassandra

`tracking-service/.../chat/persistence/ChatRepository.java`

```
1. INSERT INTO order_chat_dedup (order_id, client_message_id, message_id) VALUES (…) IF NOT EXISTS
      ├─ [applied] = true  → первая отправка: пишем сообщение, рассылаем
      └─ [applied] = false → повтор: строка-помеха содержит message_id первой попытки → вернуть то сообщение
2. INSERT INTO order_chat_message (…)          ← обычный upsert
```

- **Зачем отдельная таблица.** Обычная вставка в Cassandra — upsert, но ключ сообщения — timeuuid
  сервера, у повтора он другой, и повтор стал бы вторым сообщением.
- **Цена.** Лёгкая транзакция — это Paxos между репликами, в несколько раз медленнее обычной
  записи. Поэтому она только на короткой строке со сроком жизни сутки, а чтения идут без неё.
- **Самовосстановление.** Если сервис упал между шагами 1 и 2, повтор найдёт занятый ключ, но не
  найдёт сообщения — и допишет его с тем `message_id`, что уже занят.
- **Клиент** (`web/js/chat.js`) создаёт `clientMessageId` один раз и повторяет отправку при обрыве
  сети с тем же ключом; на ответ с кодом (400, 429) не повторяет.

## Ограничение частоты: token bucket

```
ёмкость 5 ▕█████▏   каждое сообщение забирает токен
          ▕███  ▏   пополнение — 1 токен за 2 с
          ▕     ▏   пусто → 429 Too Many Requests, Retry-After: 2
```

Ведро разрешает **всплеск** (ёмкость) и ограничивает **средний темп** (скорость пополнения).
Родственники: fixed window (проще, но пропускает двойной всплеск на границе окон), sliding window
log (точно, но хранит каждую отметку), leaky bucket (сглаживает выход в ровный поток).

| Где | Хранилище ведра | Ключ | Параметры |
|---|---|---|---|
| Шлюз, все запросы | Redis, атомарно Lua-скриптом (`RedisRateLimiter` в глобальном фильтре `RateLimitGlobalFilter`) | IP клиента | 50/с, всплеск 100 |
| Шлюз, вход и регистрация | Redis | IP клиента | запрос стоит 4 токена, 1 токен/с, ёмкость 20 |
| Чат заказа | память экземпляра (`ChatRateLimiter`) | пользователь + заказ | 5 подряд, 1 за 2 с |

**Память против Redis.** Ведро в памяти бесплатно и не ходит по сети, но у каждого экземпляра
своё: с тремя экземплярами пользователь получит тройной лимит. Для защиты чата от залипшей кнопки
этого достаточно; для лимитов, за которые платят (API партнёров), нужен общий Redis — как в шлюзе.

**Ключ шлюза — IP, и это компромисс.** Шлюз токен не проверяет (это делают сервисы), поэтому
пользователя он не знает; `X-Forwarded-For` от клиента подделывается одной строкой. Следствие:
всё, что приходит через nginx веб-интерфейса, шлюз видит с одного адреса — одним ведром. Для
локального стенда это незаметно; на сервере ключ пришлось бы брать из заголовка доверенного
балансировщика или из проверенного в шлюзе токена.

Тест с подменёнными часами — `ChatRateLimiterTest`: ведро проверяется без `sleep`.
