# 4. Интеграции: MQTT, Web Push, gRPC-стриминг, пакетные файлы, CDC, AsyncAPI

Шесть способов связать систему с внешним миром и частями самой себя. У каждого своя ниша — таблица
в конце главы помогает выбирать.

## MQTT — телефон курьера как IoT-устройство

`tracking-service/.../tracking/mqtt/`, `docker/rabbitmq/20-food-delivery.conf`

```
телефон ──MQTT (1883) / MQTT over WebSocket (/mqtt)──▶ RabbitMQ (rabbitmq_mqtt)
   PUBLISH couriers/42/deliveries/7/position  {"latitude":…, "longitude":…}
                    │ "/" → "."
                    ▼
   amq.topic, ключ couriers.42.deliveries.7.position ─▶ очередь tracking.courier-positions ─▶ tracking-service
```

- **Зачем MQTT, если есть REST.** Связь в машине рвётся в каждом тоннеле, а батарея дорогая.
  MQTT держит одно лёгкое соединение (заголовок пакета — 2 байта против сотен у HTTP), сам
  переподключается, а **QoS 1** («хотя бы один раз») доставит точку, отправленную без сети, после
  восстановления. Есть ещё «последняя воля» (last will) — брокер сообщит о пропаже клиента сам.
- **Отдельный брокер не нужен.** RabbitMQ говорит на MQTT плагином, и сообщение становится обычным
  AMQP-сообщением в `amq.topic`. Сервис читает его как любую очередь.
- **Аутентификация — HTTP-бэкенд брокера.** Заводить учётку RabbitMQ на каждого курьера нельзя, общий
  логин не скажет, кто есть кто. Брокер спрашивает tracking-service (`/internal/rabbitmq/user|vhost|
  resource|topic`): логин — id курьера, пароль — его access-токен (проверка по JWKS), писать — только
  в `couriers.<свой id>.*`. Подделать чужой id в топике нельзя: брокер отвергнет публикацию ещё до
  приложения. Сервисные учётки по-прежнему проверяет встроенный бэкенд (он первый в списке).
- **Компромисс.** Брокер проверяет пароль при подключении, а соединение живёт дольше 15-минутного
  токена. Строже — плагин OAuth 2 с проверкой срока жизни, но он требует scopes в токене.
- **Веб-интерфейс:** курьер переключает канал GPS «HTTP / MQTT» (`web/js/mqtt-gps.js`, mqtt.js).

## Web Push — уведомление при закрытой вкладке

`notification-service/.../push/`, `web/sw.js`, `web/js/push.js`

```
браузер: Notification.requestPermission → PushManager.subscribe(ключ VAPID) → {endpoint, p256dh, auth} → платформа
платформа ──POST endpoint, тело aes128gcm, Authorization: vapid t=JWT,k=…──▶ push-сервис (FCM/Mozilla/Apple)
push-сервис ──(держит до TTL, если браузер офлайн)──▶ service worker ──▶ showNotification
```

- **Шифрование «из конца в конец» (RFC 8291).** Сообщение идёт через посредника — push-сервис
  браузера, — которому содержимое знать незачем. Браузер отдаёт свой открытый ключ и секрет;
  на каждое сообщение платформа делает эфемерную пару ключей, ECDH с ключом браузера, HKDF и
  AES-128-GCM. Реализация — на JDK без библиотек, и `WebPushCryptoTest` воспроизводит пример из
  RFC 8291 **байт в байт** — проверка против спецификации, а не против самого себя.
- **VAPID (RFC 8292)** — подпись ES256 «это сообщения именно этого приложения». JDK подписывает
  ECDSA в DER, а JWT ждёт r‖s по 32 байта — частая ловушка.
- **SSRF и здесь.** Адрес подписки присылает браузер, то есть пользователь, а запрос делает наш
  сервер. Поэтому только https и только известные push-сервисы.
- **Умершие подписки.** 404/410 от push-сервиса — подписку удалить. Удаление идёт в своей транзакции
  (`REQUIRES_NEW`): отправка затем может закончиться исключением, и откат вернул бы подписку.

## gRPC server streaming — поток событий заказа для сервисов

`order-service/.../live/OrderWatchers.java`, `OrderQueryService.WatchOrder` в контрактах v1.4.0

```
клиент: WatchOrder(order_id, after_event_id) ──▶ order-service
        ◀── OrderEventView … ◀── OrderEventView … ◀── (заказ доставлен) OK, поток закрыт
```

- Тот же источник, что у SSE браузера (LISTEN/NOTIFY + «сигнал и чтение»), другой транспорт: HTTP/2,
  protobuf, строгий контракт, дедлайны. SSE — для браузеров, gRPC-стриминг — между сервисами
  (будущий потребитель — ИИ-агент, который сам напишет клиенту о задержке).
- **Обратное давление.** `onNext` в gRPC не блокируется: медленный читатель копит сообщения в буфере
  сервера. Поэтому отправка — только пока `isReady()`, остальное в очереди, дописывается из
  `onReadyHandler`. Это та же идея, что у Reactive Streams (`request(n)`).
- **Долгий вызов без транзакции:** транзакция держала бы соединение с базой всё время потока.
- Четыре вида RPC: unary (было), server streaming (это), client streaming (поток точек трека с
  устройства), bidirectional (чат) — для последних двух в проекте выбраны MQTT и WebSocket.

## Пакетные файлы — ежедневные расчёты с ресторанами

`order-service/.../settlement/` (Spring Batch 6)

```
03:00 МСК dailySettlement(date=вчера)
  aggregate (chunk 100): JDBC-курсор → комиссия → upsert settlement_line
  export (tasklet):      CSV → MinIO settlements/2026/10/settlements-2026-10-26.csv
```

- **Почему не цикл в `@Scheduled`.** Chunk-обработка (читать по одному, писать пачкой, фиксировать
  пачку транзакцией — память и транзакции не растут с объёмом), журнал запусков `BATCH_*` со
  счётчиками и перезапуск упавшего задания с места сбоя.
- **Экземпляр задания = задание + параметры.** Расчёт за 26.10 — один экземпляр; второй успешный
  запуск Batch не даст. Несколько экземпляров сервиса по расписанию стартуют одновременно — и это
  безопасно без распределённой блокировки: координатор — общий репозиторий заданий в базе.
- **Идемпотентность записи** — первичный ключ (день, ресторан) и `ON CONFLICT DO UPDATE`; ключ файла
  детерминирован — пересчёт перезаписывает, а не плодит.
- **Сутки — в часовом поясе бизнеса.** Заказ в 00:30 по Москве — это новый день, хотя в UTC ещё вчера.
- **Файл — самая старая интеграция**, и до сих пор основная с бухгалтерией и банками: CSV с BOM
  (чтобы Excel понял UTF-8) и CRLF.

## CDC — изменения прямо из журнала базы

`docker-compose.yml` (профиль `cdc`), `docker/cdc/`

```
PostgreSQL WAL (wal_level=logical) ──слот debezium_orders──▶ Debezium Server ──▶ Kafka cdc.public.customer_order
                                                                                    │
                     ClickHouse: таблица ENGINE=Kafka ──MATERIALIZED VIEW──▶ order_status_history
```

| | Outbox (как в order-service) | CDC (Debezium) |
|---|---|---|
| Что публикуется | событие предметной области, свой контракт (`OrderIntegrationEvent`) | строка таблицы как есть |
| Код в сервисе | запись в outbox + публикатор | ни строчки |
| Связь с транзакцией | событие в той же транзакции | WAL пишется при коммите — тоже атомарно |
| Задержка | интервал публикатора (2 с) | доли секунды |
| Риск | — | схема таблицы становится чужим контрактом; изменение колонки ломает потребителей |

Лучшее из обоих — **outbox + CDC**: сервис пишет события в таблицу outbox, а Debezium (Outbox Event
Router) публикует их из WAL вместо опроса. Здесь CDC показан на сырых таблицах — для аналитики,
где «схема хранения» и нужна.

- **Слот репликации держит WAL**, пока его не прочитали. Остановленный Debezium без ограничения
  заполнил бы диск базы — поэтому `max_slot_wal_keep_size=1GB`: сверх него слот теряет позицию, и
  Debezium сделает снимок заново.
- **Публикация `FOR ALL TABLES`** создаётся provisioning'ом от суперпользователя, учётка Debezium —
  только `REPLICATION` и чтение.
- **Потребитель без кода:** ClickHouse читает Kafka сам (таблица-курсор + материализованное
  представление), а одноразовый контейнер применяет идемпотентный SQL.

Включить: `DEBEZIUM_DB_PASSWORD` в `.env`, `./scripts/start.ps1 -Cdc` (ClickHouse есть без `-Light`).
Проверить: `SELECT order_id, status, changed_at FROM order_status_history ORDER BY changed_at DESC LIMIT 20`.

## AsyncAPI — контракт асинхронных каналов

`food-delivery-contracts/asyncapi/food-delivery.asyncapi.yaml`

OpenAPI описывает запрос-ответ, AsyncAPI — сообщения: серверы (Kafka, RabbitMQ, MQTT, WebSocket),
каналы (топики, очереди, адреса STOMP, вебхуки), схемы сообщений и операции «кто пишет, кто читает».
Документ не должен расходиться с кодом: `ContractsAsyncApiTest` сверяет константы топиков, а CI
проверяет документ официальным валидатором. По нему же генерируются документация (`asyncapi generate`)
и заготовки потребителей.

## Как выбирать

| Задача | Транспорт в проекте |
|---|---|
| Сервис → сервис, ответ нужен сейчас | gRPC unary |
| Сервис → сервис, поток изменений одного объекта | gRPC server streaming |
| Событие для многих сервисов, асинхронно, с историей | Kafka (outbox) |
| Задача одному обработчику, с повторами и приоритетом | RabbitMQ рабочая очередь |
| Толчок всем экземплярам | RabbitMQ fanout / PostgreSQL NOTIFY |
| Устройство → сервер, плохая сеть | MQTT |
| Сервер → браузер (вкладка открыта) | SSE / WebSocket |
| Сервер → браузер (вкладка закрыта) | Web Push |
| Сервер → чужой сервер | вебхук |
| Изменения таблиц без кода в сервисе | CDC |
| Большой объём раз в сутки, бухгалтерия | пакетный файл |
