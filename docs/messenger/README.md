# Мессенджер платформы

Личные и групповые чаты, рабочие чаты ресторанов, переписки по заказам, обращения в поддержку, вложения,
аудио- и видеозвонки, уведомления в Telegram. Код сервиса — репозиторий `food-delivery-messenger-service`
(рядом с платформой), изменения в соседях — `food-delivery-notification-service` (ветка `feature/messenger-telegram`)
и `food-delivery-api-gateway` (ветка `feature/messenger-routes`).

## Архитектура

```
браузер ──REST /api/v1/messenger/**──► nginx ──► api-gateway ──► messenger-service ──► PostgreSQL (база messenger)
   │                                                                   │   ├─► MinIO (приватный бакет messenger-attachments)
   └──WebSocket /ws/messenger (токен первым кадром)────────────────────┘   ├─► RabbitMQ: messenger.live (живые события между экземплярами)
                                                                           │            notifications.messenger ──► notification-service ──► Telegram
   браузер ◄══════════ WebRTC (медиа напрямую, P2P; TURN при необходимости) ═══► браузер
                                                                           ├─ gRPC (mTLS) ─► order-service: чей заказ, кто курьер
                                                                           ├─ gRPC (mTLS) ─► identity-service: имена, владельцы ресторанов
                                                                           └─ Kafka food-delivery.order-events ─► системные сообщения; food-delivery.audit-events ◄─ аудит
```

**Почему отдельный сервис, а не расширение существующего.** Мессенджеру нужна реляционная модель (участники,
роли в чате, курсоры прочтения, полнотекстовый поиск, транзакция «вложение + сообщение»), свои права и свой профиль
нагрузки (долгие WebSocket-соединения). tracking-service — это Cassandra и GPS, notification-service — доставка по
каналам; встраивание туда смешало бы ответственность. Цена — ещё одна JVM (`mem_limit: 512m`, профили `full` и `messenger`).

**Новых технологий нет:** поиск — PostgreSQL FTS (`russian`), файлы — существующий MinIO, шина — существующий
RabbitMQ, Telegram — существующий notification-service. Добавлен только coturn (профиль `turn`, 64 МБ) — без TURN
звонок между разными NAT не соединится.

## Три независимых уровня прав

| Уровень | Где хранится | Что решает |
|---|---|---|
| Роль в системе (CUSTOMER, RESTAURANT_OWNER, COURIER, ADMIN) | JWT от identity-service | ADMIN = поддержка: видит только обращения и жалобы |
| Должность в точке (OWNER, MANAGER, ADMINISTRATOR, OPERATOR, KITCHEN, PICKUP) | `staff_assignment` | в какие рабочие чаты точки попадает сотрудник; кто управляет сотрудниками |
| Роль в чате (OWNER, ADMIN, MEMBER) | `chat_member.role` | что можно в конкретном чате |

Администратор группы не получает прав в ресторане; руководитель точки не получает доступа к личным перепискам
сотрудников; поддержка не видит рабочих чатов и личных переписок.

### Матрица прав

| Действие | Владелец группы | Админ группы | Участник | Руководитель точки | Поддержка |
|---|---|---|---|---|---|
| Писать, отвечать, реагировать | ✓ | ✓ | ✓ (в канале — нет) | ✓ в чатах своей точки | только обращения |
| Внутренняя заметка | — | — | сторона ресторана/поддержки в переписке по заказу | ✓ | ✓ |
| Приглашать | ✓ | ✓ | если разрешил владелец | авто-чаты — по назначениям | — |
| Исключать | любого | только участников | — | увольнением/переводом | — |
| Назначать админов, передать владение, удалить группу, видимость истории | ✓ | — | — | — | — |
| Закреплять, удалять чужие сообщения | ✓ | ✓ | — (в личной переписке — закреплять) | ✓ (админ авто-чатов) | удаление по жалобе |
| Важное объявление с ознакомлением | ✓ | ✓ | — | ✓ (+ ADMINISTRATOR) | — |
| Управлять сотрудниками точки | — | — | — | OWNER — всеми, MANAGER — кроме OWNER/MANAGER | ✓ |
| Читать личные переписки сотрудников | — | — | — | **нет** | **нет** |

Кто кому может написать лично: только коллеги (одна точка или точки одной сети). Клиенты, курьеры и рестораны
общаются в переписках по заказу, с поддержкой — в обращениях.

## Минимальная кадровая модель

В платформе было только «кто управляет рестораном». Для рабочих чатов добавлено ровно необходимое: сеть
(`organization`), назначение сотрудника в точку с должностью и статусом (`staff_assignment`), приглашение по
одноразовому коду (`staff_invite`), смены (`staff_shift`). Это не кадровый учёт: ни табеля, ни ставок.
Владелец из identity-service получает назначение OWNER автоматически при первом обращении. Сотрудник
добавляется только приглашением, которое принимает сам, — без перебора чужих адресов и без согласия не добавить.

**Жизненный цикл:** приём → смена должности → временное отключение → перевод (только внутри сети) → увольнение.
После каждого шага в той же транзакции пересчитываются авто-чаты точки (общий, кухня, операторы, администраторы,
выдача, текущая смена, объявления), сторона ресторана в открытых переписках по заказам и чистятся ручные рабочие
группы точки и сети. Уволенный сразу теряет: историю и отправку, поиск, вложения (в том числе по уже выданной
ссылке), участие в звонке (его отключают из идущего), отложенные уведомления. Личные переписки остаются ему для
чтения, писать бывшим коллегам он не может.

## Переписки по заказу

Отдельный чат на назначение, общего «все со всеми» нет:

| Назначение | Состав |
|---|---|
| CUSTOMER_RESTAURANT | клиент + OWNER/MANAGER/ADMINISTRATOR/OPERATOR точки |
| CUSTOMER_COURIER | клиент + текущий курьер |
| RESTAURANT_COURIER | OWNER/MANAGER/ADMINISTRATOR/OPERATOR/PICKUP + текущий курьер |
| RESTAURANT_INTERNAL | все сотрудники точки |
| SUPPORT_CUSTOMER / _RESTAURANT / _COURIER | сторона + поддержка |

Чат создаётся, когда его впервые открывает участник. Внутренняя заметка (`audience_side`) не попадает чужой стороне
ни в истории, ни в живых событиях, ни в поиске, ни в счётчиках, ни во вложениях; ответ на неё сам становится
внутренним; закрепить и переслать её нельзя. Под полем ввода — кому будет видно сообщение.

**Смена курьера:** прежний исключается сразу (сверка при каждом обращении, по событиям заказа и фоном раз в 30 с),
новый видит историю только с момента подключения, в чате — системное сообщение.
**Завершённый заказ:** чаты с курьером закрываются на запись сразу, клиент с рестораном — через 24 ч, внутреннее
обсуждение — через 7 дней, обращения не закрываются (сообщение в решённое обращение открывает его снова).
Бывший курьер видит переписку ещё 24 ч. Через 180 дней переписка удаляется целиком вместе с файлами.

## История для новых участников

Группа: владелец выбирает «вся история» или «с момента вступления» (личные группы — по умолчанию с момента
вступления, рабочие — вся). Исключённый и вышедший теряют доступ целиком. Курьер в переписке по заказу — с момента
подключения. Сотрудник в рабочих чатах точки — вся история (рабочий контекст точки).

## Вложения

Приватный бакет MinIO, без постоянных ссылок. Тип — по сигнатуре содержимого (белый список: JPEG/PNG/GIF/WebP,
MP4/MOV/WebM, MP3/OGG/M4A, PDF, DOCX/XLSX/PPTX/ZIP, текст; HTML, SVG и исполняемые файлы отклоняются), безопасное
имя с расширением по фактическому типу, пределы 10/50/25 МБ (фото/видео/прочее), до 10 на сообщение, квота 1 ГБ на
пользователя, превью изображений. Выдача — после проверки права видеть сообщение, `nosniff`,
`Content-Security-Policy: sandbox`, Range для видео; для `<img>/<video>` — подписанная ссылка на 5 минут, права
при этом проверяются заново на каждом обращении. Загрузка: файл → READY, сообщение в своей транзакции переводит в
ATTACHED; неотправленное удаляется через сутки, объект — когда на него не осталось ссылок (пересылка создаёт
ссылку, а не копию). Проверка на вредоносное содержимое — clamd (INSTREAM), включается `ATTACHMENTS_CLAMAV_HOST`;
по умолчанию выключена (ClamAV требует ~1 ГБ памяти).

## Звонки

WebRTC, сигнализация (SDP/ICE) — кадрами `call.signal` через WebSocket и только между участниками звонка, с того
устройства, которое приняло звонок. Медиа — напрямую между браузерами; STUN/TURN — `CALLS_STUN_URLS`,
`CALLS_TURN_URLS`, `TURN_SECRET` (временные учётные данные coturn REST API). Групповые — сетка (mesh) до 4 участников:
больше требует медиасервера (SFU), его нет. Состояния: звонок → все устройства звонят → принятие на одном, остальные
перестают; занят, отклонён, нет ответа (35 с → пропущенный + уведомление), отмена, обрыв соединения (25 с на
возврат, ICE restart), запрет доступа к устройствам (участник слушает без своего звука/видео), выбор устройств,
снижение битрейта видео при потерях. Отзыв доступа к чату удаляет из звонка: остальные получают `call.removed` и
закрывают соединение (в P2P медиа рвут клиенты — сервер его не проводит). Запись не ведётся.

**Проверено:** настоящая передача аудио и видео между двумя браузерами (две вкладки встроенного браузера с разными
источниками; ICE `connected`, кадры декодируются с обеих сторон). Источник — синтетический (холст и тон,
`localStorage["fd.calls.fakeMedia"]="1"`), оба клиента на одной машине. **Не проверено:** настоящие камера и
микрофон, звонок между разными сетями через TURN, групповой звонок из трёх-четырёх браузеров.

## Telegram

Мессенджер решает кому и когда: участник ли ещё, прочитано ли (на любом устройстве), отключён ли чат (упоминания
проходят), включён ли вид чатов, тихие часы в поясе пользователя (отложить до конца), «рабочие — только в смену»,
входящий звонок — только если не в приложении. Объединение: одна строка на (пользователь, чат), ожидание
`delay_seconds` (30 с). Текст по умолчанию — без имён и содержимого (`preview=NONE`). notification-service
доставляет: ключ идемпотентности (`messenger_delivery`), 429 `retry_after` — ожидание ровно столько и не считается
попыткой, 5xx/сеть — повторы с паузой до 5 попыток, 403 «бот заблокирован» — привязка снимается, причина видна
пользователю в настройках, повторная привязка её сбрасывает. Сбой Telegram не возвращается в мессенджер.
Привязка — существующая: одноразовая ссылка `t.me/<бот>?start=<код>` (код хранится только хэшем), отвязка — из настроек.
`TELEGRAM_MESSENGER_ALLOWED_USER_IDS` — список тестовых получателей: пока он задан, настоящие сообщения уходят только им.

## Надёжность

Порядок — номер сообщения в чате (выдаётся под блокировкой строки чата). Догон после переподключения — по номеру
изменения (`/changes?since=`), который растёт на любой правке, удалении, реакции, закреплении. Повторная отправка —
идемпотентна (`clientMessageId`, уникальный индекс). Несколько устройств: прочтение синхронизируется (`read.self`),
звонок принимается на одном. Лимиты: сообщения (20 подряд, 1/с), загрузки, поиск, звонки, жалобы — плюс лимит шлюза.
Живые события публикуются после фиксации, адресаты — по базе в момент публикации.

## Модерация и аудит

Блокировка закрывает личную переписку и звонки в обе стороны и приглашения в группы; в рабочих чатах, переписках
по заказу и обращениях не действует — работа не останавливается; для конфликтов там — жалоба. Жалобу разбирает
поддержка по снимку одного сообщения, удаление — с записью в аудит. Аудит: создание групп, состав, роли, передача
владения, приём/перевод/отключение/увольнение, смены, удаление чужих сообщений — таблица `audit_log` и общий топик
`food-delivery.audit-events` (сводный журнал администратора). Текст сообщений в журналы не пишется; в логах — номера.

## Модель защиты переписки

Шифрование «в пути»: TLS на внешнем периметре (в боевом развёртывании; локальный стенд — http), mTLS между сервисами
по gRPC. Хранение: PostgreSQL и MinIO **без шифрования на уровне приложения**; сервер видит содержимое (это нужно для
поиска, модерации по жалобе, превью и уведомлений). **Сквозного шифрования (E2E) нет.** Звонки: медиа WebRTC
шифруется DTLS-SRTP между браузерами; через TURN идёт уже зашифрованным. Доступ к содержимому — только через
сервис с проверкой участия; аналитической учётке (`analytics_reader`) база мессенджера не открывается.

## Запуск и настройка

```bash
docker compose --profile full up -d
```

| Переменная | Обязательна | Что это |
|---|---|---|
| `MESSENGER_DB_PASSWORD` | да | пароль базы мессенджера (без него база не создаётся и сервис не стартует) |
| `MINIO_ROOT_USER` / `MINIO_ROOT_PASSWORD` | уже есть | вложения в том же MinIO |
| `ATTACHMENTS_LINK_SECRET` | желательно | ключ подписанных ссылок; без него — случайный на запуск |
| `MESSENGER_PUBLIC_URL` | для Telegram | адрес веб-интерфейса в ссылках «Открыть чат» (кнопка в Telegram — только для https) |
| `MESSENGER_ALLOWED_ORIGINS` | нет | откуда можно открыть WebSocket (по умолчанию `http://localhost:*`) |
| `TELEGRAM_MESSENGER_ALLOWED_USER_IDS` | для стенда | номера тестовых пользователей для настоящих сообщений |
| `CALLS_STUN_URLS` | для звонков вне одной сети | например `stun:stun.l.google.com:19302` |
| `TURN_SECRET`, `CALLS_TURN_URLS`, `TURN_EXTERNAL_IP` | для звонков через NAT | `--profile turn`; `turn:<публичный адрес>:3478` |
| `ATTACHMENTS_CLAMAV_HOST` | нет | адрес clamd для проверки файлов |

В веб-интерфейсе: «Сообщения» в меню любой роли; из заказа — «Написать ресторану/курьеру/в поддержку»; у
ресторатора — «Сотрудники и чаты» на карточке ресторана (приглашения, должности, смены, сеть); приглашение
принимается по ссылке `#/join?code=…`.
