# Postman-коллекция

Полный REST API платформы: 12 папок, 61 запрос.

## Файлы

| Файл | Что это |
|---|---|
| `food-delivery.postman_collection.json` | Коллекция запросов |
| `food-delivery.postman_environment.json` | Окружение с адресами и учётками |

## Запуск

```bash
docker compose up -d
```

Импортируйте оба файла в Postman (**Import** → перетащить), выберите окружение
«Food Delivery — локально» в правом верхнем углу и выполните папку
**01. Аутентификация** сверху вниз.

Дальше папки идут в порядке жизненного цикла заказа:

```
03 ресторан → 04 меню → 05 корзина → 06 заказ → 07 оплата → 08 готовка → 09 доставка
```

## Что заполняется само

Тесты запросов складывают в переменные коллекции всё, что нужно следующим шагам:

```
customerToken  ownerToken  courierToken  adminToken
customerId     ownerId     courierId     adminId
restaurantId   categoryId  menuItemId    cartItemId
orderId        paymentId   deliveryId
```

Руками задаются только пароли и адрес сервера — в окружении.

## Токены по ролям

Аутентификация задана на уровне папок, а не коллекции: ролей четыре, и один общий
токен пришлось бы переключать вручную перед каждым запросом. Корзина всегда ходит под
`customerToken`, управление меню — под `ownerToken`, доставка — под `courierToken`,
администрирование — под `adminToken`.

Токен живёт час. Начали прилетать 401 — повторите нужный вход из папки 01.

## Администратор

Через регистрацию роль ADMIN не выдаётся. Первая учётка создаётся при старте приложения
из `APP_ADMIN_EMAIL` и `APP_ADMIN_PASSWORD`; если переменные не заданы, администратора нет
вовсе. Те же значения впишите в `adminEmail` и `adminPassword` в окружении.

## Сквозная метка

Каждый запрос отправляет `X-Correlation-Id` и получает его обратно — коллекционный
pre-request скрипт генерирует значение вида `postman-<uuid>`. По этой метке запрос
прослеживается через логи, outbox, Kafka и потребителя:

```bash
docker compose logs app | grep postman-<uuid>
```

## Прогон целиком

Collection Runner проходит коллекцию от начала до конца: каждый запрос проверяет свой
код ответа и наличие метки корреляции.

Две оговорки. Платёжный шлюз имитированный и иногда отвечает отказом — это штатный
409, при нём папки 08 и 09 упадут следом, потому что заказ остался неоплаченным.
И запросы «Убрать блюдо/категорию из меню» в папке 04 архивируют то, что создали
предыдущие запросы, — при повторном прогоне без пересоздания они вернут 404.

## Коды ответов

| Код | Когда |
|---|---|
| 400 | Не прошла валидация запроса |
| 401 | Нет токена или он истёк |
| 403 | Роль есть, но ресурс чужой |
| 404 | Ресурс не найден |
| 409 | Операция невозможна в текущем статусе |

## Отношение к OpenAPI

`openapi/food-delivery-api.yaml` описывает только рестораны и меню — папки 03 и 04.
Остальные папки собраны по аннотациям контроллеров, живой контракт для них отдаёт
springdoc на `/swagger-ui.html`. Когда модули переедут в спецификацию, соответствующие
папки можно будет генерировать из неё.
