# Postman

Две коллекции, у каждой своя задача.

**Справочная** — `food-delivery.postman_collection.json`: полный REST API платформы,
17 папок, 77 запросов. Её открывают, чтобы посмотреть на конкретный запрос и подёргать
руками.

**Автотесты** — `food-delivery.tests.postman_collection.json`: 11 папок, 82 запроса,
прогоняется целиком и без человека. Подробности ниже, в разделе «Автотесты».

## Файлы

| Файл | Что это |
|---|---|
| `food-delivery.postman_collection.json` | Справочная коллекция запросов |
| `food-delivery.postman_environment.json` | Окружение для неё |
| `food-delivery.tests.postman_collection.json` | Коллекция автотестов |
| `food-delivery.tests.postman_environment.json` | Окружение для автотестов |
| `data/registration-cases.json` | Входные данные для data-driven папки |

## Запуск

```bash
docker compose up -d
```

Импортируйте оба файла в Postman (**Import** → перетащить), выберите окружение
«Food Delivery — локально» в правом верхнем углу и выполните папку
**01. Аутентификация** сверху вниз.

Дальше папки идут в порядке жизненного цикла заказа:

```
03 ресторан → 04 меню → 05 корзина → 06 заказ → 07 оплата → 08 готовка → 09 доставка
```

## Папки 12-16: дополнительные хранилища

Отзывы, поиск, трек курьера, рекомендации и аналитика работают только при включённых
MongoDB, Elasticsearch, Cassandra, Neo4j и ClickHouse. Поднять их:

```bash
docker compose --profile stores up -d
```

и выставить в `.env` соответствующие `STORE_*_ENABLED=true` — подробности в README проекта.

При выключенном хранилище модуля в приложении нет вовсе, вместе с его маршрутами, поэтому
запросы этих папок вернут 404. Это не ошибка коллекции: так честнее, чем 500 или пустой
список на функциональности, которой в сборке действительно нет.

Ещё две оговорки для прогона целиком. Поиск отвечает по индексу, который перестраивается
раз в пять минут, а рекомендации — по графу, который догоняется раз в полминуты; сразу
после создания данных оба вернут пустой результат. Заполнить их немедленно помогают
«Переиндексировать витрину» и «Догнать граф рекомендаций» в папке 11.

## Что заполняется само

Тесты запросов складывают в переменные коллекции всё, что нужно следующим шагам:

```
customerToken  ownerToken  courierToken  adminToken
customerId     ownerId     courierId     adminId
restaurantId   categoryId  menuItemId    cartItemId
orderId        paymentId   deliveryId
```

Руками задаются только пароли и адрес сервера — в окружении.

## Токены по ролям

Аутентификация задана на уровне папок, а не коллекции: ролей четыре, и один общий
токен пришлось бы переключать вручную перед каждым запросом. Корзина всегда ходит под
`customerToken`, управление меню — под `ownerToken`, доставка — под `courierToken`,
администрирование — под `adminToken`.

Токен живёт час. Начали прилетать 401 — повторите нужный вход из папки 01.

## Администратор

Через регистрацию роль ADMIN не выдаётся. Первая учётка создаётся при старте приложения
из `APP_ADMIN_EMAIL` и `APP_ADMIN_PASSWORD`; если переменные не заданы, администратора нет
вовсе. Те же значения впишите в `adminEmail` и `adminPassword` в окружении.

## Сквозная метка

Каждый запрос отправляет `X-Correlation-Id` и получает его обратно — коллекционный
pre-request скрипт генерирует значение вида `postman-<uuid>`. По этой метке запрос
прослеживается через логи, outbox, Kafka и потребителя:

```bash
docker compose logs app | grep postman-<uuid>
```

## Прогон целиком

Collection Runner проходит коллекцию от начала до конца: каждый запрос проверяет свой
код ответа и наличие метки корреляции.

Две оговорки. Платёжный шлюз имитированный и иногда отвечает отказом — это штатный
409, при нём папки 08 и 09 упадут следом, потому что заказ остался неоплаченным.
И запросы «Убрать блюдо/категорию из меню» в папке 04 архивируют то, что создали
предыдущие запросы, — при повторном прогоне без пересоздания они вернут 404.

## Автотесты

`food-delivery.tests.postman_collection.json` — набор, который прогоняется целиком
и заканчивается вердиктом, а не показаниями для чтения глазами.

### Запуск в Postman

Импортировать коллекцию и окружение «Food Delivery — автотесты (локально)», в Runner
выбрать коллекцию и нажать Run. Для папки 02 дополнительно указать файл данных
`data/registration-cases.json` — тогда её единственный запрос отработает семь раз,
по разу на случай.

### Запуск в Newman

```bash
npm install -g newman
newman run postman/food-delivery.tests.postman_collection.json   -e postman/food-delivery.tests.postman_environment.json   -d postman/data/registration-cases.json
```

Файл данных подаётся всей коллекции, поэтому с ним она пройдёт семь раз целиком.
Обычный порядок другой: один прогон коллекции без `-d`, и отдельный прогон папки 02
с данными:

```bash
newman run postman/food-delivery.tests.postman_collection.json   -e postman/food-delivery.tests.postman_environment.json

newman run postman/food-delivery.tests.postman_collection.json   -e postman/food-delivery.tests.postman_environment.json   -d postman/data/registration-cases.json   --folder "02. Регистрация — негатив (data-driven)"
```

Нужен Newman 6 или новее: в наборе используется `pm.execution.skipRequest()`.

### Что проверяется

| Папка | Проверки |
|---|---|
| 00 | сервис отвечает |
| 01 | регистрация и вход четырёх пользователей прогона, схема ответа с токеном, отсутствие хеша пароля в выдаче |
| 02 | валидация регистрации на семи наборах данных: пустой и кривой e-mail, короткий пароль, пустое имя, занятый адрес, роль ADMIN, несуществующая роль |
| 03 | создание ресторана и меню, публичная витрина без токена |
| 04 | 401 без токена, 403 на чужом ресурсе и на чужой роли, 404 на несуществующем, 400 на битом теле и границах пагинации |
| 05 | сквозной сценарий: корзина → заказ → оплата → готовка → доставка → трек → история событий |
| 06 | сквозной сценарий отмены и запреты после неё |
| 07 | переходы конечного автомата из неверных статусов, идемпотентность оплаты, детерминированный отказ банка |
| 08 | пять дополнительных хранилищ |
| 09 | регрессия пагинации и ленты по курсору |
| 10 | администрирование, если задана учётка |

Плюс три проверки на каждом запросе из скрипта коллекции: ответ не 5xx, время ответа
меньше пяти секунд, сквозная метка `X-Correlation-Id` вернулась той же, что ушла.

### Повторяемость

Каждый прогон заводит своих пользователей, свой ресторан и своё меню: адреса и телефоны
собираются из метки прогона, которая выставляется при регистрации. Набор можно гонять
подряд сколько угодно раз на одной базе — он не упирается в «e-mail уже занят» и не
зависит от того, что осталось от прошлых запусков. Данные за собой он не убирает:
это локальный стенд, а чистка потребовала бы административных прав.

Папки идут по порядку и передают друг другу идентификаторы. Запуск отдельной папки
из середины не сработает — это цена связности сценария.

### Пять хранилищ и отсутствующий администратор

Папка 08 считает 404 допустимым ответом: при `STORE_*_ENABLED=false` маршрута не
существует вовсе. Набор зелёный и с включёнными хранилищами, и без них — содержимое
проверяется только там, где модуль ответил.

Папка 10 пропускает свои запросы, если в окружении не заданы `adminEmail` и
`adminPassword`. Проверка прав — что клиента в административный контур не пускают —
выполняется всегда.

### Отказ банка

Заглушка платёжного шлюза отклоняет ровно один случай: сумму, оканчивающуюся на `.13`.
Папка 07 этим пользуется — заводит блюдо за 100.13 и проверяет, что после отказа заказ
остался в `CREATED`, а платёж не записался. Случайного отказа в шлюзе нет намеренно,
поэтому проверка не «мигает».

## Коды ответов

| Код | Когда |
|---|---|
| 400 | Не прошла валидация запроса |
| 401 | Нет токена или он истёк |
| 403 | Роль есть, но ресурс чужой |
| 404 | Ресурс не найден |
| 409 | Операция невозможна в текущем статусе |

## Отношение к OpenAPI

`openapi/food-delivery-api.yaml` описывает только рестораны и меню — папки 03 и 04.
Остальные папки собраны по аннотациям контроллеров, живой контракт для них отдаёт
springdoc на `/swagger-ui.html`. Когда модули переедут в спецификацию, соответствующие
папки можно будет генерировать из неё.
